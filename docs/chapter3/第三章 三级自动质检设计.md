# 第三章 三级自动质检设计

> **本章导读**：这是本项目的核心章节。我们会讲清 rubric 为什么被设计成**声明式数据**、加权打分与硬性阻断如何工作、三个闸门的职责边界，以及 21 个检查项各自的判定依据。核心文件是 `ghsqa/rubric.py` 与 `ghsqa/rules.py`。

---

## 3.1 一个关键选择：rubric 是数据，不是 `if/else`

&emsp;&emsp;最直觉的质检实现是这样写的：

```python
# ❌ 过程式写法
def check_repo(repo):
    if repo.stars > 100 and repo.has_ci and repo.test_file_count > 5:
        return "PASS"
    elif repo.stars > 50:
        return "REVIEW"
    return "REJECT"
```

&emsp;&emsp;这种写法能跑，但有三个致命问题：

| 问题 | 后果 |
| --- | --- |
| **不可审计** | 报告里只能说"总分 72"，说不清这 72 分是怎么来的 |
| **不可调参** | 想改"测试文件数阈值"，得翻遍代码找魔数 |
| **不可回归** | 逻辑散落在多个 `if` 里，改一处可能悄悄影响另一处 |

&emsp;&emsp;本项目采用**声明式**设计：每条规则是一个带元数据的对象。

```python
@dataclass
class Check:
    """一个可独立计分的质检检查项。"""
    id: str                                        # 稳定 ID，如 "REPO-03"
    title: str                                     # 展示名
    gate: str                                      # 归属闸门 ADM / REPO / MS
    fn: Callable[[Snapshot], CheckOutcome]         # 纯函数：事实 → 得分
    weight: float = 1.0                            # 权重
    hard: bool = False                             # 是否硬性阻断
    pass_at: float = 0.5                           # 通过门槛
    rationale: str = ""                            # 判定依据（必填）
    fix_hint: str = ""                             # 改进建议
```

&emsp;&emsp;这三条好处是直接对应上面的三个问题的：

- **可审计**：每个检查项有稳定 ID（`ADM-01`、`REPO-03`、`MS-04`），报告里逐条列出得分、实测值、判定依据；
- **可调参**：权重与阈值集中在 rubric 定义里，调整口径不需要改逻辑；
- **可回归**：检查项是纯函数 `Snapshot -> CheckOutcome`，fixtures 一挂就能跑，测试直接断言得分。

&emsp;&emsp;`rationale` 字段是**必填**的——回归测试会校验每一条规则都有判定依据。这不是形式主义：当你三个月后质疑"为什么这条规则给了 0.6 分"，`rationale` 就是答案。

## 3.2 打分语义

### 单条规则：输出 0 到 1

&emsp;&emsp;每个检查项输出一个 `CheckOutcome`，分数落在 **[0, 1]**：

```python
@dataclass
class CheckOutcome:
    score: float          # 0.0 ~ 1.0
    detail: str = ""      # 人读的说明（会进报告）
    measured: Any = None  # 实测原始值（供机器消费与调试）

    @classmethod
    def ok(cls, detail="", measured=None):        # 完全达标
        return cls(1.0, detail, measured)

    @classmethod
    def fail(cls, detail="", measured=None):      # 完全不达标
        return cls(0.0, detail, measured)

    @classmethod
    def partial(cls, score, detail="", measured=None):  # 部分达标
        return cls(clamp(score, 0.0, 1.0), detail, measured)
```

&emsp;&emsp;三个工厂方法覆盖了全部情形。注意 `partial()` 内部会 `clamp` 到 [0,1]，防止规则实现里的计算误差产生越界分数。

### 闸门：加权求和 × 100

```python
total_weight = sum(c.weight for c in checks) or 1.0
weighted = 0.0
for check in checks:
    outcome = check.run(snapshot)
    weighted += outcome.score * check.weight
    ...
score = clamp(weighted / total_weight * 100.0)
```

&emsp;&emsp;即：

```
闸门得分 = (Σ 检查项得分 × 权重) / Σ 权重 × 100
```

&emsp;&emsp;用**归一化**而不是简单求和，好处是闸门得分始终是百分制，直观可比。`or 1.0` 是防御性写法，避免该闸门没有任何检查项时除零。

### 三档判定

```python
if hard_failures:
    verdict = "REJECT"
elif score >= rubric.pass_score:      # 默认 75
    verdict = "PASS"
elif score >= rubric.review_score:    # 默认 60
    verdict = "REVIEW"
else:
    verdict = "REJECT"
```

| 判定 | 条件 | 含义 |
| --- | --- | --- |
| ✅ **PASS** | 得分 ≥ 75 且无硬性阻断 | 自动质检通过 |
| 🟡 **REVIEW** | 60 ≤ 得分 < 75 | 需人工介入 |
| ❌ **REJECT** | 得分 < 60 **或** 有硬性阻断 | 不合格 |

&emsp;&emsp;**注意判定的优先级**：`hard_failures` 的判断在最前面。这就是"一票否决"的实现方式——哪怕得分 99 分，只要触发硬性阻断，直接 REJECT。

## 3.3 硬性阻断机制

### 语义

&emsp;&emsp;一个检查项被标记为 `hard=True` 时：

```python
passed = outcome.score >= check.pass_at
if check.hard and not passed:
    hard_failures.append("%s（%s）" % (check.id, check.title))
```

&emsp;&emsp;一旦进入 `hard_failures` 列表，该闸门的判定**无条件变成 REJECT**。

### 为什么只有 4 项

&emsp;&emsp;21 个检查项里，只有 4 项是硬性阻断：

| ID | 检查项 | 门槛 | 为什么配得上一票否决 |
| --- | --- | --- | --- |
| `ADM-01` | 仓库公开且可访问 | 0.5 | 访问不了，一切无从谈起 |
| `ADM-02` | 仓库未归档 | 0.5 | 归档 = 已停止演进，没有真实开发节奏 |
| `MS-01` | 存在 Milestone | 0.5 | 没有任务载体，无法产出结构化任务 |
| `MS-03` | 任务边界可界定 | 0.5 | 边界不清，任务无法独立验收 |

&emsp;&emsp;这四项满足**全部三个条件**：

1. 不通过意味着后续所有质量分**失去意义**；
2. 不存在"可接受的例外"（或例外必须由人工显式豁免）；
3. 判定依据是**客观事实**，不依赖领域判断。

&emsp;&emsp;我们对 `hard` 的使用保持极度克制。如果一条规则"可能有问题但也能接受"，它就不该是硬性阻断——否则评分体系会退化成"随便一个不合意就否决"，也就失去了分级的意义。

&emsp;&emsp;反例：`ADM-04`（许可证明确）**不是**硬性阻断，因为 `NOASSERTION` 确实存在"可用于教学"的情形，需要人工读条款判断。它通过部分得分 + 进入人工复核队列来体现风险，而不是一票否决。

## 3.4 三个闸门的职责边界

&emsp;&emsp;闸门的划分不是按"重要性"，而是按**回答的问题层次**：

| 闸门 | 回答的问题 | 权重 | 性质 |
| --- | --- | --- | --- |
| **ADM** 准入 | 这个仓库**配不配**进采集池？ | 0.2 | **阻断型** |
| **REPO** Repo 质量 | 工程本身**值不值得**作为任务来源？ | 0.4 | 累积式 |
| **MS** Milestone 质量 | 这个里程碑**能否**拆成可评估的任务？ | 0.4 | 累积式 |

### 阻断型闸门：ADM 的特殊性

```python
specs = [
    GateSpec("ADM", "准入质检", 0.2, blocking=True),
    GateSpec("REPO", "Repo 质量质检", 0.4, blocking=False),
    GateSpec("MS", "Milestone 质量质检", 0.4, blocking=False),
]

for spec in specs:
    if blocked:
        skipped.append(spec.key)
        continue
    result = run_gate(rubric, snapshot, spec.key, spec.title)
    gates.append(result)
    if spec.blocking and result.verdict == "REJECT":
        blocked = True
```

&emsp;&emsp;ADM 判定 REJECT 后，后续闸门被记入 `skipped_gates` 而**不执行**。

&emsp;&emsp;为什么？因为**在明显不合格的仓库上继续算质量分是浪费**。一个已归档的仓库，测试覆盖率是 60% 还是 90%，有意义吗？没有。

&emsp;&emsp;更重要的是**语义上的诚实**：报告里直接写"REPO 与 MS 被跳过"，比给出一堆无意义的分数更准确。看这个真实输出：

```
准入闸门判定   : ❌ REJECT
硬性阻断项     : ADM-02（仓库未归档）
跳过后续闸门   : REPO, MS
最终结论       : ❌ REJECT
```

&emsp;&emsp;另外，跳过闸门后权重要重新归一化，否则综合分会被系统性压低：

```python
active_weight = sum(s.weight for s in specs if s.key not in skipped) or 1.0
overall = sum(g.score * next((s.weight for s in specs if s.key == g.gate), 0.0)
              for g in gates) / active_weight
```

## 3.5 逐条解析：准入闸门（ADM）

&emsp;&emsp;准入闸门只回答最粗的资格问题。**这一关不过，后面的质量分没有意义。**

### `ADM-01` 仓库公开且可访问 · 权重 1.0 · 🔒 硬性

&emsp;&emsp;检查仓库未被禁用、默认分支可确定。

> **判定依据**：无法访问或已被禁用的仓库不具备采集前提。

### `ADM-02` 仓库未归档 · 权重 1.0 · 🔒 硬性

&emsp;&emsp;`is_archived` 必须为 `False`。

> **判定依据**：归档仓库停止演进，无法再产出真实的开发里程碑，任务会退化为练习题。

&emsp;&emsp;这是全项目最重要的一条硬性规则。归档仓库的 Milestone 是历史遗留待办，不会有人推进——基于它设计的任务缺少真实约束。

### `ADM-03` 快照固定到不可变 commit · 权重 1.5 · 非硬性

&emsp;&emsp;检查 `pinned_ref` 是否是 40 位十六进制 sha。权重 **1.5**，高于大多数检查项。

&emsp;&emsp;判定分三档：

| 情形 | 得分 |
| --- | --- |
| 钉住 40 位 commit sha | 1.0 |
| 仅钉住可变 ref（分支名/标签） | 0.4 |
| 完全未钉住 | 0.0 |

> **判定依据**：只有钉在 commit sha 上，采集结果才可复现、可审计；分支名会随时间漂移。

### `ADM-04` 许可证明确 · 权重 1.0 · 非硬性

&emsp;&emsp;这条规则必须区分 GitHub 的**三种取值**，它们的法务含义完全不同：

```python
spdx = (repo.license_spdx or "").upper()
if spdx == "NONE":
    return CheckOutcome.fail(
        "GitHub 判定仓库无任何许可证（NONE），默认保留全部权利，不可作为采集素材", ...)
if spdx and spdx != "NOASSERTION":
    return CheckOutcome.ok("许可证：%s" % spdx, ...)
if repo.has_license_file:
    return CheckOutcome.partial(
        0.6, "仓库含 LICENSE 文件但 GitHub 未能识别为标准 SPDX 标识（%s），需人工确认授权边界", ...)
if spdx == "NOASSERTION":
    return CheckOutcome.partial(
        0.3, "许可证无法断言（NOASSERTION）且未在快照中发现 LICENSE 文件，需人工确认", ...)
return CheckOutcome.fail("未检测到任何许可证，含代码的仓库不宜作为任务来源", ...)
```

| 取值 | 得分 | 含义 |
| --- | --- | --- |
| 标准 SPDX（`MIT`/`Apache-2.0`…） | 1.0 | 授权明确 |
| `NOASSERTION` + 有 LICENSE 文件 | 0.6 | 非标准模板，需人工确认 |
| `NOASSERTION` + 无 LICENSE 文件 | 0.3 | 更可疑，需人工确认 |
| `NONE` | 0.0 | **根本没有许可证，默认保留全部权利** |
| 无任何许可证信息 | 0.0 | 不可采集 |

> **判定依据**：许可证决定采集素材能否被再分发与改造成任务，是法务前置条件。

&emsp;&emsp;**为什么区分 `NONE` 和 `NOASSERTION`？** 因为很多人会把它们混为一谈：
- `NONE` 是**没有许可证文件**——法律上作者未授予任何权利，代码公开可见 ≠ 可再分发；
- `NOASSERTION` 是**有许可证但 GitHub 无法识别成标准模板**——可能是自定义协议，也可能只是格式特殊，需要人读条款。

&emsp;&emsp;前者直接判死，后者转人工。这个区分是本项目在法务层面的一个真实经验。

### `ADM-05` 非 fork 仓库 · 权重 0.5

&emsp;&emsp;fork 得 0.5 分（部分得分，非否决）。

> **判定依据**：fork 的 issue/milestone 常继承自上游，任务归属容易被误判。

### `ADM-06` Issue 功能开启 · 权重 0.5

> **判定依据**：Milestone 依附于 issue 体系，Issue 关闭则任务边界无从采集。

### `ADM-07` 快照内容非空 · 权重 0.5

&emsp;&emsp;文件数与顶层条目不能同时为 0。

> **判定依据**：空仓库没有任何代码结构可评估，后续质量闸门必然失效。

## 3.6 逐条解析：Repo 质量闸门（REPO）

### `REPO-01` 文档完备度 · 权重 1.0

&emsp;&emsp;三个子项加权：

| 子项 | 分值 |
| --- | --- |
| 有 README | 0.5 |
| 有仓库简介（description） | 0.2 |
| 文档文件数 ≥ 阈值 | 0.3 |

&emsp;&emsp;注意阈值随仓库类型变化：

```python
threshold = 1 if tutorial else 3
```

> **判定依据**：README 与文档是理解任务上下文的第一入口，缺文档会让任务成本不可估。

### `REPO-02` 目录结构清晰 · 权重 1.0

&emsp;&emsp;分两个维度：

| 子项 | 判定 | 分值 |
| --- | --- | --- |
| 顶层条目数 | 3~40 个（有意图的模块划分） | 0.5 |
| | < 3 个（过于扁平） | 0.2 |
| | > 40 个（平铺成灾） | 0.3 |
| 最大目录深度 | ≥ 2 层 | 0.5 |
| | == 1 层 | 0.25 |

> **判定依据**：有意图的目录层级是「任务边界可界定」的结构前提，平铺仓库难以定位改动面。

&emsp;&emsp;注意这个设计：顶层条目**既不能太少也不能太多**。太少说明项目结构未展开（可能只是个脚本集合），太多说明缺乏组织（一堆文件平铺在根目录）。这是一个典型的"区间型"判定。

### `REPO-03` 测试与回归护栏 · 权重 1.5 · 非硬性

&emsp;&emsp;**权重最高的检查项之一**，因为它直接决定任务是否有意义。

```python
if _is_tutorial_like(snapshot):
    return CheckOutcome.ok("教程型仓库以文档为主，测试不作为主要验收手段...")
if not repo.code_file_count:
    return CheckOutcome.fail("未识别出任何代码文件", ...)
if not repo.has_tests_dir and repo.test_file_count == 0:
    return CheckOutcome.fail("完全没有测试文件与测试目录，任务缺乏回归护栏", ...)
score = min(1.0, ratio / 0.15)     # 15% 测试占比即满分
```

&emsp;&emsp;判定逻辑是：**没有任何测试 → 0 分**；有测试则按 `test_ratio` 线性给分，**15% 即满分**。

> **判定依据**：没有测试的仓库无法验证 AI 产出的正确性，任务验收会退化成主观判断。

&emsp;&emsp;`min(1.0, ratio / 0.15)` 这个写法值得注意：它不追求"测试越多越好"。测试占比超过 15% 后继续加分没有意义，反而可能鼓励把时间花在无谓的测试上。

### `REPO-04` 自动化与构建配置 · 权重 1.0

| 子项 | 分值 |
| --- | --- |
| 有 CI | 0.6 |
| 有依赖/构建清单 | 0.25 |
| 有容器化配置 | 0.15 |

> **判定依据**：CI 与依赖清单决定了任务能否被自动化验证，是「可评测」的工程基础。

### `REPO-05` 依赖与体积治理 · 权重 0.8

| 子项 | 分值 |
| --- | --- |
| 有依赖清单 | 0.5 |
| 语言构成可解析 | 0.25 |
| 体积 ≤ 200 MB | 0.25 |

> **判定依据**：体积过大或依赖缺失会让快照成本与复现难度失控。

### `REPO-06` 社区活跃度 · 权重 1.2

&emsp;&emsp;三个维度加权：**0.5 × 提交新鲜度 + 0.3 × 近期提交量 + 0.2 × 贡献者规模**。

&emsp;&emsp;提交新鲜度按天数分档：

| 最近提交 | 得分 |
| --- | --- |
| ≤ 30 天 | 1.0 |
| ≤ 90 天 | 0.8 |
| ≤ 365 天 | 0.5 |
| > 365 天 | 0.1 |

&emsp;&emsp;贡献者规模：≥10 人满分，≥3 人 0.6，≥1 人 0.3。

> **判定依据**：活跃仓库的里程碑才反映真实开发节奏，也是任务多样性的来源。

### `REPO-07` 任务可切分性 · 权重 1.0

| 子项 | 判定 | 分值 |
| --- | --- | --- |
| 文件数 | ≤ 2000（规模可控） | 0.5 |
| 最大目录深度 | ≤ 6 层 | 0.3 |
| 有代码/文档入口 | — | 0.2 |

> **判定依据**：规模与层级决定了能否把仓库拆成粒度合适、可独立验收的任务。

## 3.7 逐条解析：Milestone 质量闸门（MS）

### `MS-01` 存在 Milestone · 权重 1.0 · 🔒 硬性

&emsp;&emsp;仓库至少要有一个里程碑。

> **判定依据**：Milestone 是本流程的任务载体；完全没有里程碑的仓库无法产出结构化任务。

### `MS-02` 目标 Milestone 可定位 · 权重 1.0

&emsp;&emsp;如果用户用 `--milestone` 指定了目标，它必须真实存在于快照中。未指定时这条规则给满分并标注"信息性"。

> **判定依据**：指定的里程碑必须真实存在于该快照，否则整轮质检会评错对象。

&emsp;&emsp;这条规则防的是一个很容易发生的错误：**参数打错了但流程照跑不误**。比如写成 `--milestone 999`，如果没有这条检查，流程会静默地评估一个错误的里程碑。

### `MS-03` 任务边界可界定 · 权重 1.4 · 🔒 硬性

&emsp;&emsp;**Milestone 闸门里权重最高的一项**，四个子项：

| 子项 | 判定 | 分值 |
| --- | --- | --- |
| 里程碑描述 | ≥ 40 字符 | 0.4 |
| 任务数 | 3 ~ 30 个（粒度适中） | 0.4 |
| | < 3 个（边界过窄） | 0.15 |
| | > 30 个（需拆批次） | 0.15 |
| 设定了截止时间 | — | 0.1 |
| 尚在进行中 | — | 0.1 |

> **判定依据**：有描述、任务数适中的里程碑才能被切成边界清晰、可独立交付的工作单元。

&emsp;&emsp;"3~30 个任务"这个区间是核心经验值：
- **少于 3 个**：边界过窄，无法构成一个有意义的开发阶段；
- **多于 30 个**：粒度过粗，应该拆成多个批次，否则单个任务与里程碑的对应关系会模糊。

### `MS-04` 任务可验收信息 · 权重 1.3

&emsp;&emsp;三个可验收性信号加权：

```
得分 = 0.5 × 正文充分率 + 0.3 × 标签覆盖率 + 0.2 × 指派覆盖率
```

&emsp;&emsp;其中"正文充分率"是 `body_length >= 120` 的 issue 占比。

> **判定依据**：issue 正文、标签与负责人共同构成验收标准的原材料，缺失会让评估失焦。

&emsp;&emsp;如果快照里没有 issue 明细（只有聚合计数），这条规则给 0.3 分并说明原因——**诚实标注"无法评估"比假装评估更有价值**。

### `MS-05` 结果可验证 · 权重 1.2

| 子项 | 分值 |
| --- | --- |
| 仓库有 CI | 0.4 |
| 有测试资产（或教程型豁免） | 0.4 |
| 完成度健康（≥80% 或 0%） | 0.2 |

> **判定依据**：任务成果必须能被客观验证，测试与 CI 是成本最低的验证手段。

### `MS-06` 任务体量健康 · 权重 0.9

&emsp;&emsp;按完成度分档：

| 完成度 | 得分 | 含义 |
| --- | --- | --- |
| ≥ 75% | 1.0 | 已交付的高质量里程碑 |
| 30% ~ 75% | 0.75 | 进行中，任务信息鲜活 |
| > 0 且 < 30% | 0.5 | 偏低，可能停滞 |
| == 0% | 0.6 | 尚未开始，方向明确但无交付证据 |
| 任务数 == 0 | 0.0 | 空壳里程碑 |

> **判定依据**：全空或长期停滞的里程碑缺少真实约束，难以反映工程判断力。

&emsp;&emsp;注意 0% 完成给 0.6 而不是 0——**尚未开始的里程碑并非没有价值**，它至少说明了开发方向。但 0 任务的空壳里程碑直接判 0。

### `MS-07` 协作痕迹 · 权重 0.8

| 子项 | 分值 |
| --- | --- |
| 被指派人 ≥ 2 位（1 位得 0.2） | 0.4 |
| 讨论 ≥ 5 条（有讨论得 0.15） | 0.3 |
| 跨多个时间点创建 | 0.3 |

> **判定依据**：多人参与与讨论记录说明任务经过真实评审，边界与验收更可信。

## 3.8 两个容易做错的地方

### 陷阱一：不能用"文档占比高"识别教程型仓库

&emsp;&emsp;这是本项目在开发过程中**真实踩过的坑**。最初的实现是这样写的：

```python
# ❌ 错误的实现
TUTORIAL_DOC_RATIO = 0.5
if repo.doc_ratio >= TUTORIAL_DOC_RATIO and repo.doc_file_count >= 5:
    return True
```

&emsp;&emsp;看起来合理：文档占比超过 50% 且文档数不少于 5 个，就认为是教程型项目。

&emsp;&emsp;**但这会把大量常规库误判成教程。** 比如 `psf/requests`、`django/django` 这类项目，`docs/` 目录下有几百个 `.rst` 文件，文档占比可能远超 50%。它们会被错误地豁免测试检查——而测试恰恰是它们最宝贵的资产。

&emsp;&emsp;正确的判据是**文档文件数超过代码文件数**：

```python
# ✅ 正确的实现
def _is_tutorial_like(snapshot: Snapshot) -> bool:
    """判断仓库是否为教程/文档型项目。

    注意：不能只用「文档占比高」来判定，否则带大型 ``docs/`` 目录的常规库
    （如 requests、django）会被误判。真正的教程型项目特征是**文档文件数超过代码文件数**，
    即内容本身就是交付物，代码只是配套示例。
    """
    repo = snapshot.repo
    if repo is None:
        return False
    topics = {t.lower() for t in repo.topics}
    if topics & set(TUTORIAL_TOPIC_HINTS):     # agent/llm/tutorial/guide...
        return True
    if repo.doc_file_count >= TUTORIAL_MIN_DOCS and repo.doc_file_count > repo.code_file_count:
        return True
    return False
```

&emsp;&emsp;两种判据的差别在哪里？

| 判据 | requests 场景 | hello-agents 场景 | 是否可用 |
| --- | --- | --- | --- |
| 文档占比 ≥ 50% | 误判为教程 ❌ | 正确识别 ✅ | ❌ |
| 文档数 > 代码数 | 正确排除 ✅ | 正确识别 ✅ | ✅ |

&emsp;&emsp;根本区别在于**语义**：教程型项目的特征是"**内容本身就是交付物**"——文档是主体，代码只是配套示例。而 requests 的 `docs/` 是**API 文档**，是代码的附属品，代码才是主体。

&emsp;&emsp;还有一个额外信号：`topics` 包含 `tutorial`/`course`/`book`/`education`/`guide` 等关键词时直接判定。这是最明确的声明。

### 陷阱二：`NONE` 和 `NOASSERTION` 不是一回事

&emsp;&emsp;已在 `ADM-04` 中详述，这里强调核心区别：

```python
if spdx == "NONE":
    return CheckOutcome.fail(...)          # 0 分：无许可证，不可采集
if repo.has_license_file:
    return CheckOutcome.partial(0.6, ...)  # 0.6 分：有文件但非标准，转人工
```

&emsp;&emsp;很多采集工具把它们当作同一个"许可证未知"的状态处理，这是有法务风险的。

## 本章小结

&emsp;&emsp;本章的核心要点：

1. **rubric 是声明式数据，不是 `if/else`。** 每条规则有稳定 ID、权重、判定依据、改进建议，带来可审计、可调参、可回归三大好处。`rationale` 是必填字段。

2. **打分链路**：单条规则输出 [0,1] → 闸门内按权重归一化 × 100 → 对照 `pass_score=75` / `review_score=60` 判 PASS/REVIEW/REJECT。**硬性阻断的判断优先级最高**。

3. **只有 4 项硬性阻断**：`ADM-01`、`ADM-02`、`MS-01`、`MS-03`。它们满足"不通过则后续分数失去意义""无合理例外""判定依据客观"三个条件。对 `hard` 的使用必须极度克制。

4. **ADM 是阻断型闸门**：REJECT 后跳过 REPO 与 MS，并重新归一化权重。这既是性能优化，也是语义上的诚实。

5. **两个真实的实现陷阱**：
   - 教程型仓库不能用"文档占比高"识别（会误判 requests/django），正确判据是**文档文件数 > 代码文件数**；
   - `NONE`（无许可证，判 0 分）与 `NOASSERTION`（非标准许可证，判 0.6 转人工）法务含义完全不同，不可混为一谈。

6. **测试护栏权重 1.5**，因为它直接决定任务是否有意义——没有测试的仓库，AI 的产出无法被客观验证。
