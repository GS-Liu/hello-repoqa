# 第六章 扩展与二次开发

> **本章导读**：到这里你已经理解了本项目的完整流程与判定逻辑。本章讲**如何按你的需求改造它**：新增质检规则、调整权重阈值、接入新的数据源（GitLab/Gitee）、扩充 fixtures、增加人工质检问题、扩展报告格式。核心原则是——**改动应该局部化，不要污染既有的分层**。

---

## 6.1 扩展点总览

&emsp;&emsp;本项目的分层设计决定了它天然有明确的扩展点。先看一张"改哪里"的对照表：

| 你想做的事 | 改哪个文件 | 是否需要动其它层 |
| --- | --- | --- |
| 新增一条质检规则 | `rules.py` | 否（加测试即可） |
| 调整权重 / 通过阈值 | `rules.py`、`rubric.py` | 否 |
| 接入 GitLab / Gitee | 新增采集函数 + `collector.py` 分派 | **否**（规则层零改动） |
| 补充演示/回归场景 | `fixtures/` | 否 |
| 增加人工质检问题 | `manual.py` | 否 |
| 扩展报告格式 | `report.py` | 否 |
| 改变闸门组织方式 | `pipeline.py` | 否 |

&emsp;&emsp;这张表能这么"干净"，完全得益于[第二章](../chapter2/第二章%20固定快照采集原理.md)讲的事实层/规则层解耦：**只要 `Snapshot` 结构不变，采集、规则、人工、报告四层就能各自独立演进。**

## 6.2 新增一条质检规则

&emsp;&emsp;我们用一条完整的例子走通全流程：**新增"仓库是否包含安全策略（SECURITY.md）"检查**。

### 第一步：确定它属于哪个闸门

| 闸门 | 回答的问题 |
| --- | --- |
| `ADM` | 这个仓库**配不配**进采集池 |
| `REPO` | 工程本身**值不值得**作为任务来源 |
| `MS` | 这个里程碑**能否**拆成可评估的任务 |

&emsp;&emsp;"有没有安全策略"是关于**工程规范度**的，属于 `REPO` 闸门。

### 第二步：编写检查函数

&emsp;&emsp;检查函数必须是**纯函数**：输入 `Snapshot`，输出 `CheckOutcome`，**不得访问网络、不得读环境变量**。

&emsp;&emsp;在 `rules.py` 的 `repo_checks()` 内部添加：

```python
def has_security_policy(snapshot: Snapshot) -> CheckOutcome:
    """检查仓库是否提供安全策略文件，用于判断漏洞上报路径是否明确。"""
    repo = snapshot.repo
    if repo is None:
        return _missing(snapshot)          # 复用既有的缺事实处理
    if repo.has_security_policy:           # 假设已加了这个字段，见下文
        return CheckOutcome.ok("存在 SECURITY.md", measured={"found": True})
    return CheckOutcome.fail("缺少安全策略，漏洞上报路径不明确", measured={"found": False})
```

&emsp;&emsp;注意两点：

1. **复用 `_missing(snapshot)`**。仓库事实缺失时统一返回同一个失败结论，不要自己造错误信息。
2. **填 `measured`**。它是实测原始值，会进入报告 JSON，是排查"为什么这条规则给了这个分"的关键线索。

### 第三步：如果需要新的结构信号

&emsp;&emsp;如果 `RepoFacts` 里还没有你要的字段，就在 `models.py` 加字段、在 `collector.py` 的 `derive_structure()` 里填充：

```python
# models.py —— RepoFacts 里加字段
has_security_policy: bool = False
```

```python
# collector.py —— derive_structure() 里初始化与判定
repo.has_security_policy = False
...
for item in file_list:
    low = item.lower
    ...
    if low.split("/")[-1] in ("security.md", "security.rst"):
        repo.has_security_policy = True
```

> ⚠️ **别忘了 fixtures**。`derive_structure()` 只在提供了 `files[]` 清单时才会跑；如果你的 fixtures 只用预聚合信号，需要在 `repo.json` 里直接写上 `has_security_policy`，否则新字段永远是默认值。

### 第四步：决定是否设为硬性阻断

&emsp;&emsp;**请极度克制地使用 `hard=True`。** 只有同时满足以下三条才配得上一票否决：

- 不通过意味着后续所有质量分**失去意义**；
- 不存在"可接受的例外"，或例外必须由人工显式豁免；
- 判定依据是**客观事实**，不依赖领域判断。

&emsp;&emsp;"缺少 SECURITY.md"**不满足**第 2、3 条——很多小型库没有安全策略但完全可用。所以它是**非硬性**的。

### 第五步：注册检查项

&emsp;&emsp;加到 `repo_checks()` 返回的列表里，**填满所有字段**：

```python
Check(
    id="REPO-08",                       # 闸门前缀 + 两位序号
    title="安全策略",
    gate="REPO",
    fn=has_security_policy,
    weight=0.6,                         # 权重为正
    hard=False,
    pass_at=0.5,                        # 得分达到该值才算通过
    rationale="安全策略决定漏洞上报路径是否明确，影响任务的可维护性评估。",
    fix_hint="优先选择带有 SECURITY.md 的仓库；缺失时在报告中标注为已知风险。",
),
```

&emsp;&emsp;几个约定：

| 字段 | 约定 |
| --- | --- |
| `id` | 闸门前缀 + 两位序号，**必须全局唯一**（测试会校验） |
| `weight` | 为正数。参考量级：核心规则 1.5，重要 1.0~1.2，辅助 0.5~0.8 |
| `pass_at` | 默认 0.5。若规则是"部分得分即可"的性质，可降到 0.4 |
| `rationale` | **必填**。测试会校验每条规则都有判定依据 |
| `fix_hint` | 强烈建议填。它会出现在人工复核队列里，指导下一步动作 |

### 第六步：补充测试

&emsp;&emsp;在 `code/tests/run_tests.py` 里增加断言，**至少覆盖达标与不达标两条路径**：

```python
def test_security_policy_rule() -> None:
    section("[X] 安全策略规则")
    from ghsqa.rubric import DEFAULT_RUBRIC, run_gate
    from ghsqa.collector import collect
    from ghsqa.models import SnapshotRequest

    snap = collect(SnapshotRequest(repo="acme/widget-toolkit"),
                   source="fixtures", fixtures_dir=FIXTURES)
    gate = run_gate(DEFAULT_RUBRIC, snap, "REPO", "Repo 质量质检")
    row = next((c for c in gate.checks if c["id"] == "REPO-08"), None)
    check(row is not None, "REPO-08 已注册并执行")
```

&emsp;&emsp;然后运行 `python -m tests.run_tests` 确认全部通过。注意：**新增检查项后，原有的断言可能因为权重变化而失效**（闸门得分会变），需要一并更新。

## 6.3 调整权重与阈值

### 闸门级阈值

&emsp;&emsp;在 `rubric.py` 的 `_build_default_rubric()` 里：

```python
def _build_default_rubric() -> Rubric:
    return Rubric(
        name="hello-repoqa/default",
        version="1.0.0",          # 改口径时请一并升级版本号
        pass_score=75.0,          # PASS 门槛
        review_score=60.0,        # REVIEW 门槛
        checks=admission_checks() + repo_checks() + milestone_checks(),
    )
```

&emsp;&emsp;调参的影响：

| 调整 | 效果 |
| --- | --- |
| 提高 `pass_score` | 更多仓库落到 REVIEW，人工负担上升但更安全 |
| 降低 `review_score` | 更多仓库判 REJECT，误杀风险上升 |
| 缩小两者差距 | REVIEW 区间收窄，人工介入减少但边界更硬 |

&emsp;&emsp;**注意一个不变式**：`review_score < pass_score`。回归测试里有一条断言专门校验它，写反了会被测出来。

### 检查项级权重

&emsp;&emsp;权重决定某条规则在闸门得分中的话语权。当前量级参考：

| 权重 | 含义 | 项目中的例子 |
| --- | --- | --- |
| 1.5 | 核心，直接决定任务是否有意义 | `ADM-03`、`REPO-03` |
| 1.4 | 高度重要 | `MS-03` |
| 1.2~1.3 | 重要 | `REPO-06`、`MS-04`、`MS-05` |
| 1.0 | 标准 | 大多数规则 |
| 0.8~0.9 | 辅助 | `REPO-05`、`MS-06`、`MS-07` |
| 0.5 | 弱信号 | `ADM-05`、`ADM-06`、`ADM-07` |

&emsp;&emsp;调整权重时请同时更新受影响的测试断言——闸门得分是加权和，改一个权重会牵动整张表。

### 版本号

&emsp;&emsp;`Rubric.version` 会写进报告的 JSON：

```json
"rubric": {"name": "hello-repoqa/default", "version": "1.0.0"}
```

&emsp;&emsp;**改动判定口径时请升级版本号**。这样历史报告的结论就有据可查——你能分清"两份报告结论不同"是因为仓库变了，还是因为 rubric 变了。

## 6.4 接入新的数据源

&emsp;&emsp;这是本架构最优雅的扩展点。假设你要接入 **Gitee**。

### 核心契约

&emsp;&emsp;你只需要做一件事：**产出一个结构相同的 `Snapshot`**。

```python
Snapshot(
    request=request,
    collected_at=now_iso(),
    source="gitee",              # 标注数据源
    repo=repo,                   # RepoFacts
    milestones=milestones,       # List[MilestoneFacts]
    warnings=[...],
)
```

&emsp;&emsp;只要 `RepoFacts` 与 `MilestoneFacts` 的关键字段被填好，**下游 21 条规则、人工质检、报告渲染全部零改动**。

### 实现步骤

**第一步：写采集函数**

```python
# collector.py
def collect_from_gitee(request: SnapshotRequest, token: Optional[str] = None,
                       max_pages: int = 5) -> Snapshot:
    """从 Gitee OpenAPI 采集，产出与 GitHub 采集同构的 Snapshot。"""
    owner, name = request.owner, request.name
    # 1) 拉仓库元信息
    raw = _gitee_get("/repos/%s/%s" % (owner, name), token)
    # 2) 解析 ref 为 commit sha
    commit_sha = _gitee_resolve_ref(owner, name, request.ref or raw["default_branch"], token)
    # 3) 拉文件树
    files = [FileFacts(path=n["path"], size=n.get("size") or 0, is_dir=n["type"] == "tree")
             for n in _gitee_tree(owner, name, commit_sha, token)]
    # 4) 构造 RepoFacts —— 字段名映射到本项目的模型
    repo = RepoFacts(
        full_name=raw["full_name"], owner=owner, name=name,
        description=raw.get("description"), default_branch=raw["default_branch"],
        language=raw.get("language"), stars=raw.get("stargazers_count") or 0,
        forks=raw.get("forks_count") or 0, open_issues=raw.get("open_issues_count") or 0,
        license_spdx=(raw.get("license") or {}).get("spdx_id"),
        created_at=raw.get("created_at"), pushed_at=raw.get("pushed_at"),
        commit_sha=commit_sha,
    )
    # 5) 复用同一套结构信号推导 —— 关键！
    derive_structure(repo, files)
    # 6) 拉 Milestone 与 issue 明细
    milestones = _gitee_milestones(owner, name, request, token, max_pages)
    return Snapshot(request=request, collected_at=now_iso(), source="gitee",
                    repo=repo, milestones=milestones)
```

&emsp;&emsp;**第 5 步是最关键的**：一定要调用 `derive_structure(repo, files)`，而不是自己另写一套结构推导。这样新数据源产出的结构信号与 GitHub 完全一致，规则层才能无缝工作。

**第二步：在 `collect()` 里分派**

```python
def collect(request, source="api", fixtures_dir=None, ...):
    if source == "fixtures":
        ...
    if source == "gitee":
        return collect_from_gitee(request, max_pages=max_pages)
    if source != "api":
        raise CollectError("未知数据源：%r（可选 api / fixtures / gitee）" % source)
    return collect_from_api(request, ...)
```

**第三步：在 CLI 里放开选项**

```python
sp.add_argument("--source", choices=["api", "fixtures", "gitee"], default="api", ...)
```

&emsp;&emsp;就这三步。**规则、报告、人工质检一行都不用改。**

### 字段映射注意事项

&emsp;&emsp;跨平台映射时有几个坑：

| 字段 | 注意点 |
| --- | --- |
| `commit_sha` | **必须填**。填不上 `ADM-03` 会扣分，快照也不可复现 |
| `pushed_at` | 用于活跃度判定。格式须是 ISO8601 |
| `license_spdx` | **务必区分 `NONE` 与 `NOASSERTION`**，两者的法务含义不同（见[第三章](../chapter3/第三章%20三级自动质检设计.md)） |
| `is_archived` | 若平台无对应概念，显式设为 `False`，不要留 `None` |
| `is_pull_request` | 很多平台的 issue 接口会混入 PR，务必标记，否则污染任务数 |
| `body_length` | 只记长度，不要存正文 |

## 6.5 扩充 fixtures

&emsp;&emsp;fixtures 既是演示样例也是回归用例。**我们尤其欢迎边界场景**。

### 目录结构

```
fixtures/<owner>__<repo>/          # 注意是双下划线
├── repo.json
└── milestones.json
```

&emsp;&emsp;命名由这一行决定，所以要严格对应：

```python
slug = request.repo.replace("/", "__")     # "acme/widget-toolkit" → "acme__widget-toolkit"
```

### `repo.json` 字段清单

| 字段 | 说明 | 被谁使用 |
| --- | --- | --- |
| `full_name` | `owner/repo` | — |
| `description` | 仓库简介 | `REPO-01` |
| `license_spdx` | `MIT` / `NOASSERTION` / `NONE` | `ADM-04` |
| `default_branch` | 默认分支名 | `ADM-01` |
| `language` | 主语言 | 报告展示 |
| `topics` | 主题标签数组 | 教程型识别 |
| `stars` / `forks` / `watchers` | 社区数据 | 报告展示 |
| `open_issues` | open issue 数 | 报告展示 |
| `size_kb` | 体积（KB） | `REPO-05` |
| `is_archived` | **归档开关** | `ADM-02`（硬性） |
| `is_fork` | fork 开关 | `ADM-05` |
| `has_issues` | Issue 是否开启 | `ADM-06` |
| `created_at` / `pushed_at` | ISO8601 时间 | `REPO-06` |
| `commit_sha` | **40 位十六进制** | `ADM-03` |
| `commit_count_recent` | 近期提交数 | `REPO-06` |
| `contributor_count` | 贡献者数 | `REPO-06` |
| `languages` | `{语言: 字节数}` | `REPO-05` |
| `files[]` | 文件清单，每项需 `path`，可选 `size` / `is_dir` | `derive_structure()` |

### `milestones.json` 字段清单

每个 Milestone：

| 字段 | 说明 | 被谁使用 |
| --- | --- | --- |
| `number` | 编号（`--milestone` 按此匹配） | `MS-02` |
| `title` | 标题 | `MS-02` |
| `description` | **目标描述** | `MS-03`（判定 ≥40 字符） |
| `state` | `open` / `closed` | 报告展示 |
| `due_on` | 截止时间 | `MS-03` |
| `open_issues` / `closed_issues` | 聚合计数 | `MS-06`（完成任务数） |
| `issues[]` | 任务明细 | `MS-04`、`MS-07` |

每个 issue：

| 字段 | 说明 | 被谁使用 |
| --- | --- | --- |
| `number` / `title` | 编号与标题 | 报告展示 |
| `state` | `open` / `closed` | `MS-06` 完成度 |
| `labels[]` | 标签数组 | `MS-04` 标签覆盖率 |
| `assignees[]` | 负责人数组 | `MS-04`、`MS-07` |
| `body_length` | **正文长度**（阈值 120） | `MS-04` 正文充分率 |
| `comments` | 评论数 | `MS-07` 协作痕迹 |
| `is_pull_request` | 是否 PR | 任务数统计 |
| `created_at` / `closed_at` | 时间 | `MS-07` 跨时间点判定 |

### ⚠️ 必须提供 `files[]`

&emsp;&emsp;这是最容易忽略的一点。如果不提供，采集层会走退化路径：

```python
if files:
    derive_structure(repo, files)
else:
    # 退化为直接使用 fixtures 提供的聚合信号
    repo.file_count = int(raw_repo.get("file_count") or 0)
    ...
    warnings.append("fixtures 未提供 files 清单，已退化为使用预聚合结构信号")
```

&emsp;&emsp;退化后你必须手动填 `file_count` / `code_file_count` / `test_file_count` / `doc_file_count` / `max_depth` / `has_ci` / `has_manifest` / `has_tests_dir` / `top_level_entries` 等全部字段。

&emsp;&emsp;**更重要的是**：退化路径会跳过 `derive_structure()`，意味着**你的 fixtures 覆盖不到结构推导逻辑**。作为回归用例，它的价值会大打折扣。

### 验证你的 fixtures

```bash
cd code
python -m ghsqa check --repo <owner>/<repo> \
  --source fixtures --fixtures ../fixtures \
  --out ../out/tmp
```

&emsp;&emsp;检查三件事：

1. 判定结果是否符合你的预期；
2. 报告里有没有 `fixtures 未提供 files 清单` 之类的 warning；
3. **明确这个场景要验证哪条规则**——这是 fixtures 存在的意义。

&emsp;&emsp;参考现有的三个场景，它们各自的目标很明确：

| 场景 | 类型 | 预期判定 | 验证目标 |
| --- | --- | --- | --- |
| `datawhalechina/hello-agents` | 教程型 | ✅ PASS | 教程型豁免、活跃度、任务边界 |
| `acme/widget-toolkit` | 常规工程 | ✅ PASS | 测试护栏、CI、协作痕迹 |
| `legacycorp/abandoned-metrics-lib` | 已归档 | ❌ REJECT | `ADM-02` 硬性阻断 + 跳过闸门 |

## 6.6 增加人工质检问题

&emsp;&emsp;人工问题对应的是**机器的能力边界**。在 `manual.py` 里扩充 `MANUAL_QUESTIONS`：

```python
MANUAL_QUESTIONS: List[Dict[str, str]] = [
    ...
    {
        "id": "H-06",
        "question": "该仓库是否存在跨仓库的隐式依赖，导致任务无法在本仓库内独立完成？",
        "why": "机器只能看到单仓库的文件树，无法推断仓库之间的运行时耦合关系。",
    },
]
```

&emsp;&emsp;三个字段的分工：

| 字段 | 作用 |
| --- | --- |
| `id` | 稳定标识，会出现在 `init-review` 模板与报告的裁决表里 |
| `question` | 人要回答的具体问题，必须可判定 |
| `why` | **为什么机器判不准**——这是设计依据，也是说服评审人的关键 |

&emsp;&emsp;新增后会自动生效：`blank_review_template()` 会为它生成 `pending` 裁决，`apply_review()` 会要求它被裁决后才能放行。

### 与复核队列的配合

&emsp;&emsp;注意人工介入有**两个入口**，它们是互补的：

| 入口 | 来源 | 回答什么 |
| --- | --- | --- |
| `MANUAL_QUESTIONS`（H-01~H-05） | 固定的能力边界清单 | "机器**原理上**判不准什么" |
| `build_review_queue()` | 自动质检的边界结论 | "这次**具体**哪里存疑" |

&emsp;&emsp;如果你的新问题实际上只对特定场景适用，更好的做法是**新增一条质检规则并让它进入复核队列**，而不是加进 `MANUAL_QUESTIONS`——后者会给所有仓库都增加一条待裁决项，抬高人工成本。

### ⚠️ 关于 `apply_review()` 的联动

&emsp;&emsp;新增问题后，**所有既有的人工结论 JSON 都会变成"未完成"**，因为新问题没有裁决记录：

```python
unresolved = [d.question_id for d in review.unresolved()]     # verdict in (pending, followup)
if unresolved:
    blocking.append("人工质检仍有 %d 条未裁决" % len(unresolved))
    return {"final_verdict": "REVIEW", ...}
```

&emsp;&emsp;这是**有意的设计**：口径变了，旧的人工结论自然需要重新确认。如果你在 CI 里维护了固定的 review JSON，记得同步更新。

## 6.7 扩展报告

&emsp;&emsp;`report.py` 提供两个渲染函数，扩展点不同。

### Markdown 报告

&emsp;&emsp;`render_markdown(result, with_details=True)` 按章节拼接。想看某个章节怎么生成的，直接搜对应的标题字符串即可，例如：

```python
lines.append("## 四、三级自动质检")
```

&emsp;&emsp;几个约定：

- 表格用标准 Markdown 语法，注意列数对齐；
- 单元格内容用 `truncate()` 裁剪，避免超长文本破坏表格；
- 长文本（如 `desc`）用" | "分隔前先清理换行——`truncate()` 内部已经做了 `" ".join(str(text).split())`。

### JUnit XML

&emsp;&emsp;`render_junit(result)` 把每个闸门映射成一个 `<testsuite>`，每个检查项映射成一个 `<testcase>`：

```python
<testsuite name="Repo 质量质检 (REPO)" tests="7" failures="0">
  <testcase name="REPO-01 文档完备度" classname="REPO"/>
  ...
  <testcase name="REPO-03 测试与回归护栏" classname="REPO">
    <failure message="score=0.00">完全没有测试文件与测试目录，任务缺乏回归护栏</failure>
  </testcase>
</testsuite>
```

&emsp;&emsp;跳过闸门会渲染成 `<skipped/>`，这样 CI 界面能正确显示"未执行"而不是"失败"。

&emsp;&emsp;扩展时注意 **XML 转义**——所有动态内容都要过 `escape()` 或 `quoteattr()`，否则仓库名里的特殊字符会破坏 XML 结构。

## 6.8 性能与配额注意事项

&emsp;&emsp;在线采集时，这几个参数直接决定成本：

| 参数 | 作用 | 建议 |
| --- | --- | --- |
| `--max-pages` | 分页请求上限（默认 5，每页 100 条） | 超大仓库保持默认；需要完整贡献者列表时调大 |
| `GITHUB_TOKEN` | 提升配额 | 匿名 60 次/小时，认证 5000 次/小时 |
| `--no-archive` | 跳过 tarball 下载 | 仓库体积 > 1 GB 时建议加上 |
| `--ref <sha>` | 直接指定 commit | 省掉一次 ref 解析请求，且更明确 |

&emsp;&emsp;单仓库的 API 请求量大致是：

```
1 (repos) + 1 (commits/ref) + 1 (trees) + 1 (contributors) + 1 (languages)
+ 1 (commits) + ceil(milestones/100) + ceil(issues/100)
```

&emsp;&emsp;通常 8~12 次请求。匿名配额（60 次/小时）能跑 5 个左右的仓库，批量采集请务必配置 token。

### 三个性能设计点

&emsp;&emsp;回顾一下已经内置的优化，扩展时请保持这些约定：

1. **只对目标 Milestone 拉取 issue 明细**。有几十个里程碑的仓库全量拉取会产生大量请求，而质检只需要目标里程碑。
2. **只存结构信号，不存内容**。文件只保留路径/大小/sha，issue 只记 `body_length`。
3. **归档下载失败只降级为 warning**。commit sha 才是必需的，tarball 是加分项。

- [ ] fixtures 场景的预期判定已在 PR 描述中说明

## 本章小结

&emsp;&emsp;本章的核心要点：

1. **扩展点由分层设计决定**：新增规则改 `rules.py`，接入新数据源改 `collector.py`，两者互不干扰。**只要 `Snapshot` 契约不变，规则层零改动。**

2. **新增检查项的六步**：定闸门 → 写纯函数 → （必要时）加结构信号 → 决定是否硬性 → 注册并填满字段 → 补测试。`rationale` 必填，`hard` 慎用。

3. **接入新数据源的关键是复用 `derive_structure()`**，而不是另写一套结构推导——这样新平台产出的信号与 GitHub 完全一致。跨平台映射时要特别注意 `license_spdx` 的 `NONE`/`NOASSERTION` 区分、`commit_sha` 必须填、PR 必须标记。

4. **fixtures 必须提供 `files[]` 清单**，否则会走退化路径，跳过结构推导逻辑，作为回归用例的价值大打折扣。

5. **人工问题与复核队列是两个互补入口**：前者是固定的能力边界清单，后者是本次运行的具体存疑项。扩充 `MANUAL_QUESTIONS` 会让既有 review JSON 全部变为"未完成"——这是有意的口径变化保护。

6. **性能与配额**：单仓库约 8~12 次 API 请求；批量采集请配置 `GITHUB_TOKEN`；大仓库用 `--no-archive`。

&emsp;&emsp;到这里，本教程的六章就全部结束了。你现在应该能够：采集任意仓库的固定快照、读懂三级质检的每一分是怎么来的、完成单轮人工终审、并按照自己的需求改造这套流程。

&emsp;&emsp;如果这个项目对你有帮助，欢迎给它一个 Star，或者把你遇到的边界场景作为 fixtures 贡献回来——**每一个真实的坑，都值得变成一条规则。**
