# 前言

> **本章导读**：在正式开始之前，我们先说清楚三件事——这个项目因何而生、写给谁看、以及你该怎么读它。

---

## 一、项目缘起

&emsp;&emsp;过去一年，AI Coding 从一个新鲜概念变成了真实的工程实践。越来越多的团队开始构建**任务数据集**：从真实开源仓库里挑出有代表性的开发任务，用来评测、训练或微调编码智能体。

&emsp;&emsp;但真正动手之后你会发现，最难的部分根本不是写代码，而是**判断**：

- 这个仓库值不值得采集？
- 这个 Milestone 能不能拆成一个个边界清晰、可以独立验收的任务？
- 采下来的东西，三个月后还能复现吗？

&emsp;&emsp;现实中，这套判断往往靠人工翻仓库、凭经验拍板。结果是三个典型病症：**口径不一致**（换个人评判结论就变了）、**结论不可复现**（当时为什么选它，没人说得清）、**隐藏陷阱多**（归档仓库、无许可证、空壳里程碑、没有任何测试）。

&emsp;&emsp;`hello-repoqa` 想做的事情很具体：**把这套判断固化成可自动执行、可审计、可回归的流程**。

&emsp;&emsp;它不是一个"评分脚本"，而是一条完整的流水线：

```
采集固定快照 → 准入质检 → Repo 质量质检 → Milestone 质量质检 → 单轮人工质检 → 报告
```

---

## 二、这个项目有什么不一样

&emsp;&emsp;市面上不缺仓库分析工具，但本项目的三个设计选择值得你先了解：

**第一，快照钉在 commit 上，而不是分支名。** 分支会漂移，`main` 今天和明天不是同一个东西。只有 40 位的 commit sha 才是不可变锚点，采集结果才谈得上"可复现"。

**第二，事实层与规则层彻底解耦。** 采集器只负责产出**事实**（仓库有多少文件、有没有 CI、里程碑有几个任务），规则只负责**读事实**做判断。带来的直接好处是：同一套 21 条质检规则，既能跑在线的 GitHub API，也能跑离线的本地 fixtures——**规则代码零修改**。这也是它能被塞进 CI 稳定回归的前提。

**第三，人工只做一轮，但机器判不准的部分必须显式留痕。** 自动质检覆盖可量化的部分；法务判断（许可证边界）、领域判断（任务隐含前提）、价值判断（阈值边缘该不该放行）交给人工。而且——**只要没提交人工结论，最终判定最多是 REVIEW，绝不放行**。

## 三、写给谁看

&emsp;&emsp;本项目面向：

- 熟悉 **GitHub 与 Git 版本管理**，理解 commit / branch / milestone / issue 这些概念；
- 有**真实软件工程经验**，知道什么叫测试护栏、CI、依赖治理；
- 是**开源贡献者**或希望成为开源贡献者，理解一个仓库的"质量"该如何评判；
- 对 AI Coding 任务设计有兴趣，想知道一个可评测的任务应该如何界定边界。

**前置知识**：

| 项目 | 要求 |
| --- | --- |
| Python | 能读懂类、函数、dataclass 即可，不需要高级特性 |
| Git / GitHub | 熟悉 commit、分支、Milestone、Issue 的基本用法 |
| 软件工程 | 理解测试、CI、依赖清单的作用 |
| 网络 | **不需要**——本项目可以完全离线运行 |

**环境要求**：

- Python **3.8 或更高版本**
- **零第三方依赖**（只用标准库，不需要任何 `pip install`）

## 五、五分钟跑通

### 第一步：获取代码

```bash
git clone https://github.com/<your-name>/hello-repoqa.git
cd hello-repoqa/code
```

### 第二步：确认环境（离线即可）

&emsp;&emsp;跑一遍回归测试，58 项断言全部通过就说明环境没问题：

```bash
python -m tests.run_tests
```

&emsp;&emsp;预期输出结尾：

```
============================================================
全部通过：58 项断言
```

### 第三步：跑一遍完整流水线

&emsp;&emsp;用内置 fixtures 对一个真实的教程型仓库做质检（**无需网络**）：

```bash
python -m ghsqa check \
  --repo datawhalechina/hello-agents \
  --source fixtures --fixtures ../fixtures \
  --milestone 3 \
  --out ../out/demo
```

&emsp;&emsp;你会看到三个闸门的得分与判定：

| 闸门 | 得分 | 判定 |
| --- | --- | --- |
| 准入质检 (ADM) | 93.33 | ✅ PASS |
| Repo 质量质检 (REPO) | 97.33 | ✅ PASS |
| Milestone 质量质检 (MS) | 93.24 | ✅ PASS |
| **综合** | **94.90 / 100** | **🟡 REVIEW** |

&emsp;&emsp;注意最后一行的 **REVIEW**。自动质检三项全 PASS，综合 94.90 分——但因为**还没有提交人工结论**，流程有意不放行。这正是本项目的核心设计之一，我们会在[第四章](./chapter4/第四章%20单轮人工质检.md)详细展开。

### 第四步：看一份更直观的示例

&emsp;&emsp;`examples/quickstart.py` 会把采集、质检、人工复核、反面场景串起来演示一遍：

```bash
python examples/quickstart.py
```

### 第五步：试试反面场景

&emsp;&emsp;看看一个已归档仓库会被如何拦截：

```bash
python -m ghsqa check \
  --repo legacycorp/abandoned-metrics-lib \
  --source fixtures --fixtures ../fixtures \
  --out ../out/abandoned
```

&emsp;&emsp;结果会是 **REJECT**，命中 `ADM-02`（仓库未归档）硬性阻断，并且**后续两个闸门直接被跳过**——既然仓库已归档，再算 Repo 质量分没有意义。

## 六、常用命令速查

```bash
# 查看全部 21 个检查项及其判定依据
python -m ghsqa list-checks

# 只采集快照，不质检
python -m ghsqa snapshot --repo <owner>/<repo> --ref <sha> --out ../out/snap

# 完整质检（在线）
GITHUB_TOKEN=<token> python -m ghsqa check --repo <owner>/<repo> --milestone <n> --out ../out/run

# 生成人工质检模板
python -m ghsqa init-review --repo <owner>/<repo> --reviewer "Your Name" --out out/review.json

# 带人工结论重跑，输出 JUnit XML 给 CI
python -m ghsqa check --repo <owner>/<repo> --review out/review.json --junit --out ../out/final
```

## 七、获取帮助

- 遇到规则误判？欢迎提 Issue，并附上 `--out` 生成的 `*.report.json`，它能完整复现你的判定链路。
- 想新增规则？请先阅读 [CONTRIBUTING.md](../CONTRIBUTING.md)，里面写清了新增检查项的完整约定。
- 想理解某个得分为什么是 0.75 而不是 1.0？`python -m ghsqa list-checks` 会打印每条规则的 `rationale`（判定依据）与 `fix_hint`（改进建议）。
