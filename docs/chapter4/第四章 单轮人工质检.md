# 第四章 单轮人工质检

> **本章导读**
>
> 跑到这里，你可能已经注意到一个刺眼的现象：**即便自动结论是 `PASS`，最终结论依然可能停在 `REVIEW`**。
>
> 这不是 bug，而是整个流水线最重要的设计选择。本章回答三个问题：为什么自动质检后还需要人工、而且**只做一轮**？人工到底要回答哪 5 个问题、为什么偏偏是它们？人工结论又是怎么和自动分数**合并**成最终放行判定的？
>
> 学完本章，你能独立走完一次「生成模板 → 评审人填写 → 带结论重跑」的闭环，并说清每条最终结论的来源。

---

## 1. 为什么机器判完了还要人来判

### 1.1 自动质检的能力边界

`code/ghsqa/rules.py` 的模块注释里有句话定下了基调：

> 每条规则都是纯函数，输入 `Snapshot`，输出 `CheckOutcome`；不访问网络、不读环境变量。

纯函数意味着**可复现、可回归、可审计**，这是最大的优点。但反过来，机器只能看到快照里能被结构化的东西：文件数、目录深度、SPDX 标识、issue 正文字数、评论条数、完成度百分比。下面三类问题，恰好是这些数字结构性覆盖不到的。

### 1.2 机器判不准的三类问题

| 类别 | 典型场景 | 为什么机器判不准 |
| --- | --- | --- |
| **法务判断**（许可证边界） | 仓库是 MIT，但 `docs/` 下混进了第三方截图与商标素材 | 机器只能匹配 SPDX 标识字符串，读不懂 LICENSE 里的附加条款，更看不出哪些文件是第三方素材 |
| **领域判断**（任务隐含前提） | 里程碑描述写了 80 个字，看着充实，但全文没提「需要 GPU」 | 正文字数只是**代理指标**；描述是否可执行需要领域知识，不是长度能衡量的 |
| **价值判断**（阈值边缘该不该放行） | 某检查项得 0.74，差 0.01 就能进「通过」区间 | 分数是连续的，但「放行 / 不放行」是二值的。边界画在哪是**价值判断**，不是计算问题 |

第三类最微妙：不是「机器算错了」，而是「机器算对了，但这个分档本身需要有人背书」。自动分给出一个数字，把它变成「可以进入采集池」的承诺，必须有人签名。

### 1.3 为什么是「单轮」

`manual.py` 的 docstring 给出了答案：流程设计为 **自动三级质检 → 人工单轮终审**，人工只做一次，但必须对每条存疑项给出明确裁决与理由，形成可追溯的审计记录。

单轮设计同时满足两个诉求：

1. **控制成本**。人工是这条流水线上最贵的一环。多轮会签会让评审成本翻倍甚至数倍，而边际收益不成比例。更要命的是——如果评审可以无限轮次，它就会退化成「再看一眼」的拖延，而不是决策。
2. **保证决策留痕**。单轮 ≠ 随便。这一轮必须**逐条**对 5 个固定问题给出裁决和理由，并被打上时间戳。人工的每次放行都有明确署名和依据，而不是一句模糊的「我看过了」。

一句话：**用机器把可量化的部分做到极致，把不可量化的部分压缩成一次必须留痕的人类决策。**

## 2. 五个固定问题：`MANUAL_QUESTIONS`

### 2.1 为什么问题清单是写死的

`MANUAL_QUESTIONS` 是 `manual.py` 里的模块级常量，5 条，每条带 `id` / `question` / `why` 三个字段。写死而不是让评审人自由发挥，有三个好处：**ID 稳定**（`H-01`~`H-05`，报告、JSON、审计日志都能按 ID 追溯）；**`why` 字段是写给评审人看的**，明确告知「这个问题为什么不能交给机器」，避免走过场；**可回归**——`init-review` 模板和报告里的问答清单渲染的是同一份数据源，永远一致。

### 2.2 逐条解读

**`H-01` 许可证边界（法务判断）**

> **问题**：许可证是否真的允许我们把该仓库的代码/文档用作采集素材并再分发？
> **why**：自动质检只能识别 SPDX 标识，无法判断附加条款、第三方素材与商标限制。

自动侧对应 `ADM-04 许可证明确`，它区分三种情况：`NONE` → 0 分（GitHub 判定无任何许可证，默认保留全部权利）；`NOASSERTION` 或无法识别 → 0.6 / 0.3 部分分；标准 SPDX 标识（如 `MIT`）→ 1.0 满分。

问题就出在满分那条路上。`ADM-04` 拿到 1.0，只证明「GitHub 把这个仓库识别成了 MIT」。它**不能**证明：LICENSE 里有没有附加条款（比如「仅限非商业用途」）；仓库里有没有混入以其他许可证分发的第三方代码；名称、logo、截图等商标素材是否允许再分发。这三件事都要在读文本的基础上做**法务判断**。

它排在第一位，因为许可证问题是一票否决性质的——后面所有质量分都建立在「我们有权采集」这个前提之上。

**`H-02` 目录结构的真实性（领域判断）**

> **问题**：仓库的目录结构是否真实反映了任务边界？是否存在大量生成代码/二进制/归档文件干扰判断？
> **why**：机器只能统计层级与文件数，无法区分手写代码与自动生成产物。

自动侧对应 `REPO-02 目录结构清晰`，看的是「顶层条目是否落在 3~40」和「最大目录深度是否 ≥ 2」。这是个合理的形式化代理，但它看不见内容：`src/generated/` 下 800 个 protobuf 生成文件，和 800 个手写模块，在机器眼里都是「800 个文件」；一个 `dist/` 里躺着打包产物的仓库文件数会虚高，但可切分的任务边界其实很窄。**手写代码 vs 自动生成产物**这个区分需要看内容甚至项目惯例。

**`H-03` 任务隐含前提（领域判断）**

> **问题**：目标 Milestone 的任务描述是否包含足够的隐含前提（环境、数据、外部依赖）？
> **why**：正文长度只是代理指标，真正的可执行性需要领域知识判断。

自动侧对应 `MS-03 任务边界可界定`，其中一项是「里程碑描述长度 ≥ 40 字给 0.4 分」。规则本身没错——描述太短的里程碑确实不可用。但它只是**代理指标**：「实现模型推理服务，输出与参考实现一致的分数」长度完全够，可它没说明**需要 GPU、需要哪个数据集、参考实现在哪里**。这些隐含前提是否交代清楚，只有具备该领域经验的人才能一眼看出。机器看到的是字数，人看到的是可执行性。

**`H-04` 第三方可复现性（领域判断）**

> **问题**：该里程碑产出的任务，其验收标准能否由第三方独立复现？
> **why**：测试与 CI 存在不等于验收路径清晰，需要人工确认复现步骤。

自动侧对应 `MS-05 结果可验证`：「有 CI 加 0.4、有测试资产加 0.4、完成度合适加 0.2」。这条启发式衡量的其实是**验证基础设施的存在性**，而不是**验收路径的清晰度**。两者的差距可能很大：CI 只跑 lint 不跑功能测试；测试依赖公司内网的 fixture 数据；测试能跑但「什么算通过」没写在任何地方，只存在于原作者脑子里。

**`H-05` 快照完整性（采集边界）**

> **问题**：快照是否遗漏了影响任务的关键要素（子模块、LFS、私有依赖、数据文件）？
> **why**：API 采集的文件树无法反映 submodule 内容与 Git LFS 指针的真实大小。

这条直指 `collector.py` 的采集机制：在线采集走 GitHub 的 git trees API，拿到的只是文件树节点列表。于是 **submodule** 在树里只是一个 commit 指针条目，指向的**真实内容根本不在快照里**；**Git LFS** 文件在树里是一条正常记录，但 `size` 是**指针文件的大小**（通常一百多字节），不是真实资产的大小；私有依赖、需登录才能下载的数据文件同理不可见。

也就是说，快照看起来「有 52 个文件、体积 4.1 MB，一切正常」，但可能缺了最关键的那份模型权重。这必须由人来看。

### 2.3 五个问题与盲区的映射

| 问题 | 类别 | 对应自动检查项 | 盲区本质 |
| --- | --- | --- | --- |
| H-01 | 法务判断 | `ADM-04` | SPDX 标识 ≠ 授权边界 |
| H-02 | 领域判断 | `REPO-02` | 文件数 ≠ 手写代码量 |
| H-03 | 领域判断 | `MS-03` | 字数 ≠ 可执行性 |
| H-04 | 领域判断 | `MS-05` | 有 CI ≠ 验收路径清晰 |
| H-05 | 采集边界 | **无直接对应项** | 文件树 ≠ 完整内容 |

注意 H-05 在自动侧没有对应检查项——这正是它必须由人回答的原因。

## 3. 人工裁决的取值语义

### 3.1 `decisions[].verdict`：单条裁决

`HumanDecision` 数据类上的 `verdict` 字段默认 `"pending"`，可选值 `pending | accept | reject | followup`：

| 取值 | 含义 | 对最终判定的影响 |
| --- | --- | --- |
| `pending` | 尚未裁决（模板默认值） | 计入**未裁决**，阻止放行 |
| `accept` | 已确认通过，无异议 | 无阻断影响 |
| `reject` | 已确认存在硬性问题 | **无直接阻断**，须配合 `overall=reject` |
| `followup` | 需要进一步跟进 / 补充材料 | 计入**未裁决**，阻止放行 |

这里有个容易踩的坑：`reject` 和 `followup` 的行为**并不对称**。`unresolved()` 方法把它写得很直白：

```python
def unresolved(self) -> List[HumanDecision]:
    return [d for d in self.decisions if d.verdict in ("pending", "followup")]
```

`pending` 和 `followup` 都会进入 `unresolved`，导致最终判定卡在 `REVIEW`；而 `reject` **不会**——它是一条「已完成」的裁决，只是结论是不通过。真正让最终结论变成 `REJECT` 的是 `overall`。

所以正确用法是：**单条问题判 `reject` 时，务必把 `overall` 也设成 `reject` / `rework`**，否则这条否决意见不会体现在最终结论里。

### 3.2 `overall`：整体终审结论

`ManualReview` 上的 `overall` 字段默认 `"pending"`，可选值 `pending | approve | reject | rework`：

| 取值 | 含义 | 最终判定 |
| --- | --- | --- |
| `pending` | 未提交（模板默认值） | `REVIEW`（除非自动结论已是 `REJECT`） |
| `approve` | 人工终审通过 | 见 §4.4，可能是 `PASS` / `REVIEW` / `REJECT` |
| `reject` | 人工判定拒绝 | **`REJECT`** |
| `rework` | 人工判定需返工 | **`REJECT`** |

`reject` 和 `rework` 的最终判定都是 `REJECT`，区别只在语义和报告文案：前者显示「人工判定拒绝」，阻断原因 `人工终审结论：reject`；后者显示「人工判定需返工」，阻断原因 `人工终审结论：rework`。建议约定：`reject` 用于「这个仓库/里程碑根本不合适」，`rework` 用于「方向可以，但这批材料需要重新准备」。对 CI 而言两者等价，对人而言这个区分有管理价值。

## 4. 复核队列与合并规则

### 4.1 `build_review_queue()` 的三个触发条件

自动质检跑完后，`pipeline.py` 调用 `manual.build_review_queue(gates)`，从全部检查项里挑出**需要人工重点看一眼**的条目。核心判断只有一行：

```python
borderline = 0.4 <= score < 0.75
if (is_hard and score < 1.0) or borderline or not passed:
```

| 触发条件 | 代码 | `reason` 文案 | 设计意图 |
| --- | --- | --- | --- |
| **硬性项未满分** | `is_hard and score < 1.0` | 硬性检查项未满分，需确认是否可放行 | 见 §4.2 |
| **得分落模糊区间** | `0.4 <= score < 0.75` | 得分处于模糊区间，机器难以定论 | 抓及格线上下的灰色地带 |
| **未过门槛** | `not passed`（`score < pass_at`） | 未达通过门槛（pass_at=0.60） | 明确的不通过项，必须看 |

三个条件在 `if / elif / else` 里有**优先级顺序**：先判「硬性项未满分」，再判「未达通过门槛」，最后才是「模糊区间」。所以一条「硬性项且未通过」的记录显示的是「硬性检查项未满分」而非「未达通过门槛」——这是有意的，硬性阻断是更严重的信号，应优先提示。

### 4.2 为什么硬性项「通过了也要再看一眼」

这是整个设计里最反直觉的一条。一般我们理解门槛是二值的：过了就是过了。但这里对 `hard=True` 的检查项用的是 `score < 1.0` 而不是 `not passed`——**一项硬性检查即使已达到 `pass_at`、判定为 ✅，只要没拿满分，依然会进复核队列**。

原因在 `rubric.py` 的硬性阻断语义：`run_gate()` 发现 `hard_failures` 非空时，**无论总分多高都直接判 `REJECT`**，这就是一票否决。当前 rubric 里被标记为硬性的一共 4 项，`code/tests/run_tests.py` 明确断言了这一点：

```
硬性阻断项符合设计（ADM-01, ADM-02, MS-01, MS-03）
```

`ADM-01` 仓库公开且可访问、`ADM-02` 仓库未归档、`MS-01` 存在 Milestone、`MS-03` 任务边界可界定——这些都是「不合格就没有继续讨论意义」的前置条件。正因为后果严重，二值门槛就不够了：`pass_at` 只是画了一条线，**线附近的通过是脆弱的**。

举个实际例子。`acme/widget-toolkit` 的报告里 `MS-03 任务边界可界定` 得 0.90，远超 `pass_at=0.5`，判定 ✅ 🔒，没触发硬性阻断，但它被放进了复核队列。人工要确认什么？看它的构成：描述长度 0.4 + 任务数适中 0.4 + 有截止时间 0.1 = 0.9。缺的 0.1 是「尚在进行中」条件（`total_issues == open_issues`）——该里程碑有 10 个任务、完成度 60%，没拿到。这 0.1 的缺失本身无害，但**「任务边界可界定」值不值得为它放行，需要人签字**。

一句话：**硬性项的每一次非满分通过，都是对「一票否决」边界的试探，这种试探必须由人来承担。**

### 4.3 规则一：人工未提供结论 → 最多 `REVIEW`，不得放行

```python
if review is None or review.overall == "pending":
    return {
        "final_verdict": "REVIEW" if final_verdict != "REJECT" else "REJECT",
        "manual_state": "未执行人工质检",
        "blocking": ["缺少单轮人工质检结论"] if final_verdict != "REJECT" else [],
        "unresolved": [q["id"] for q in MANUAL_QUESTIONS] if final_verdict != "REJECT" else [],
    }
```

两种情况都走这条：压根没传 `--review`（`review is None`），或传了但 `overall` 还是 `pending`。关键在那个三元表达式：自动结论不是 `REJECT` → 降级为 `REVIEW` 并列出全部 5 个问题；自动结论已是 `REJECT` → 保持 `REJECT`，此时 `blocking` 和 `unresolved` 都是空表，因为**已经不需要人工来救它了**。

实测（两个 fixture 的自动结论都是 `PASS`）：

```
G auto=PASS  review=None      -> REVIEW | 未执行人工质检 | blocking=['缺少单轮人工质检结论']
                                            | unresolved=['H-01','H-02','H-03','H-04','H-05']
H auto=REJECT review=None     -> REJECT | 未执行人工质检 | blocking=[] | unresolved=[]
```

这条是整个流程的**安全底座**：只要人没签字，无论自动分多高都不可能拿到退出码 0。`run_tests.py` 的 `test_positive_path` 正是断言这一点。

### 4.4 规则二：人工 `reject` / `rework` → 最终 `REJECT`

无条件 `REJECT`，**不看自动结论**。这是人工权威压过机器分数的直接体现，`run_tests.py` 有专门用例盯住它（「人工 reject 覆盖自动 PASS」）。注意这两条分支把 `unresolved` 原样带出，但没加进 `blocking`——因为「人工拒绝」本身就是结论。

### 4.5 规则三：人工 `approve` 但仍有未裁决项 → 保持 `REVIEW`

```python
if unresolved:
    blocking.append("人工质检仍有 %d 条未裁决" % len(unresolved))
    return {"final_verdict": "REVIEW", "manual_state": "人工质检未完成",
            "blocking": blocking, "unresolved": unresolved}
```

即使 `overall` 已写成 `approve`，只要还有 `pending` 或 `followup`，就不能放行。`blocking` 带未裁决的**条数**，`unresolved` 带**具体 ID 列表**。实测 `approve` + 4 条 pending → `REVIEW`，「人工质检仍有 4 条未裁决」；`approve` + 1 条 `followup` → 同样 `REVIEW`。

这条防的是「偷懒式通过」：只填 `overall=approve`，5 个问题一个没答。**实操提醒**：`approve` 之前务必确认 5 条 `verdict` 都已从 `pending` 改成 `accept` 或 `reject`。

### 4.6 规则四：人工 `approve` 且全部裁决完毕 → 依自动分，但硬性阻断仍可能 `REJECT`

**情况 A：存在硬性阻断 → 仍然 `REJECT`。** 这是本章第三个反直觉处。人工全部 `accept`、`overall` 也 `approve` 了，为什么还是 `REJECT`？因为 `has_hard_failure` 代表某个硬性检查项得分**低于自己的 `pass_at`**。源码注释写明的是「硬性阻断**未被人工显式豁免**时仍为 REJECT」，而当前实现里 **`ManualReview` 上没有任何字段能表达豁免**（只有 `reviewer` / `reviewed_at` / `overall` / `decisions` / `notes`）。所以只要 `has_hard_failure` 为真，`approve` 就救不回来：

```
C auto=REJECT approve/all-accept hard=True -> REJECT | 人工通过但硬性阻断未豁免
                                           | blocking=['存在硬性阻断且未被显式豁免']
```

这是刻意的保守设计：人工的 `accept` 只是对 5 个定性问题的回答，不构成对硬性技术故障的豁免。要让这类仓库通过，正确做法是**回到上游解决硬性项**，而不是在评审环节签字放行。

**情况 B：无硬性阻断 → 依自动分给 `PASS` / `REVIEW`。** 注意这里的三元表达式，是最容易误解的一点：自动 `PASS` → 最终 `PASS`；自动 `REVIEW` → 最终 `REVIEW`；自动 `REJECT` → **降级为 `REVIEW`**，不是 `REJECT`。

也就是说，在「无硬性阻断 + 人工全部 accept + overall approve」这个前提下，自动的 `REJECT` 会被**提升**到 `REVIEW`。为什么？因为无硬性失败时自动 `REJECT` 只可能来自加权总分没过 `review_score`（60 分）——这是一个**价值判断**问题，而人工已明确表示看过了。结论从「机器说不行」变成「机器说不行，但人已复核，待定」是合理的。

### 4.7 兜底分支

如果 `overall` 是个不认识的值（既不是 `pending` / `reject` / `rework` / `approve`），走到最后会返回 `REVIEW` + `manual_state = "人工状态未知：<值>"` + `blocking = ["人工结论状态不可识别"]`。实测 `overall="weird"`、5 条全 `accept` 时确实得到 `REVIEW`。这是个 fail-safe：认不出的状态一律按「需要人看」处理，绝不误放行。

### 4.8 合并规则总表

| 人工状态 | 未裁决项 | 硬性阻断 | 自动结论 | **最终结论** | `manual_state` |
| --- | --- | --- | --- | --- | --- |
| 未提供 / `pending` | — | — | PASS / REVIEW | `REVIEW` | 未执行人工质检 |
| 未提供 / `pending` | — | — | REJECT | `REJECT` | 未执行人工质检 |
| `reject` | 任意 | 任意 | 任意 | `REJECT` | 人工判定拒绝 |
| `rework` | 任意 | 任意 | 任意 | `REJECT` | 人工判定需返工 |
| `approve` | 有 | 任意 | 任意 | `REVIEW` | 人工质检未完成 |
| `approve` | 无 | **有** | 任意 | `REJECT` | 人工通过但硬性阻断未豁免 |
| `approve` | 无 | 无 | PASS | `PASS` | 人工终审通过 |
| `approve` | 无 | 无 | REVIEW | `REVIEW` | 人工终审通过 |
| `approve` | 无 | 无 | REJECT | `REVIEW` | 人工终审通过 |
| 其他值 | 任意 | 任意 | 任意 | `REVIEW` | 人工状态未知：`<值>` |

## 5. 完整工作流演示

所有命令在 `code/` 目录下执行，`fixtures` 在上一级目录。

### 5.1 第一步：生成人工质检模板

```bash
python -m ghsqa init-review --repo acme/widget-toolkit \
    --reviewer "Your Name" --out out/review.json
```

`init-review` **只有三个参数**：

| 参数 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `--repo` | ✅ | — | 仓库标识，形如 `owner/repo` |
| `--reviewer` | ❌ | `""` | 评审人署名 |
| `--out` | ❌ | `review.json` | 模板输出路径 |

它的实现是调用 `blank_review_template()` 拿到全 `pending` 的模板，落盘前再塞两个下划线开头的字段：`_instructions`（写给评审人的操作说明，含下一步该跑的命令）和 `_question_bank`（完整的 5 个问题及其 `why`，让评审人不必翻源码就知道每条在问什么、为什么机器判不了）。输出：

```
已生成人工质检模板：out/review.json
需裁决 5 个问题（对应自动质检的能力边界）
```

退出码 `0`。

### 5.2 第二步：评审人填写

模板的骨架是 `reviewer` / `reviewed_at` / `overall` / `notes` / `decisions`，`decisions` 数组里是 5 条全 `pending` 的裁决。评审人要做三件事：

1. 把每条 `decisions[].verdict` 从 `pending` 改成 `accept` / `reject` / `followup`；
2. 在对应的 `note` 里写清理由（**这一步很重要**，它是审计记录的核心内容）；
3. 把 `overall` 从 `pending` 改成 `approve` / `reject` / `rework`。

```json
{
  "reviewer": "Your Name",
  "reviewed_at": null,
  "overall": "pending",
  "notes": "",
  "decisions": [
    { "question_id": "H-01", "verdict": "pending", "note": "",
      "reviewer": "", "decided_at": null }
  ],
  "_instructions": ["..."],
  "_question_bank": ["..."]
}
```

填好之后：

```json
{
  "reviewer": "Your Name",
  "reviewed_at": null,
  "overall": "approve",
  "notes": "H-02 提到的 dist/ 产物已确认不影响任务切分。",
  "decisions": [
    { "question_id": "H-01", "verdict": "accept",
      "note": "MIT 许可证，LICENSE 全文无附加条款；docs/ 截图已确认全部自研。",
      "reviewer": "", "decided_at": null },
    { "question_id": "H-05", "verdict": "accept",
      "note": "无 submodule；无 LFS 指针；无私有依赖。",
      "reviewer": "", "decided_at": null }
  ]
}
```

注意 `reviewed_at`、`decided_at`、decision 级别的 `reviewer` 都还留着空值——**不用手填**，下一步会自动补（见 §6）。

### 5.3 第三步：带结论重新质检

```bash
python -m ghsqa check --repo acme/widget-toolkit \
    --source fixtures --fixtures ../fixtures --milestone 7 \
    --review out/review.json --out out
```

`acme/widget-toolkit` 的自动结论是 `PASS`（综合 96.14/100），无硬性阻断，人工又全部 `accept` + `overall=approve`，所以最终 `PASS`，退出码 `0`：

```bash
$ python -m ghsqa check ... --review out/review.json --out out --quiet
[PASS] acme/widget-toolkit | 自动 PASS | 综合 96.14/100
$ echo $?
0
```

不带 `--review` 跑同一条命令对比一下就非常清楚——自动分完全一样，只是没人签字：

```bash
$ python -m ghsqa check ... --out out --quiet
[REVIEW] acme/widget-toolkit | 自动 PASS | 综合 96.14/100
$ echo $?
1
```

### 5.4 第四步：确认报告里的合并结果

带结论重跑后，报告「五、单轮人工质检」会从问答清单变成裁决表格：人工状态显示「人工终审通过」，并列出评审人、评审时间，以及每条问题的裁决与备注。同时「一、总览」里两行会分叉（自动结论 vs 最终结论）。而**未提交**人工结论时，「五」会退化成问答清单，并显式提示：

```markdown
- 人工状态：**未执行人工质检**
- 🚫 阻断原因：缺少单轮人工质检结论
- 尚未提交人工质检结论 → 最终判定最多为 REVIEW，不得放行。
```

## 6. 审计留痕：`sync_review_status()`

如果由评审人手填 `reviewed_at` 和 `decided_at`，会出现三种情况：忘填、填错格式、填个假的——审计记录最怕这个。所以 `pipeline.py` 在合并**之前**先调用 `sync_review_status(review)` 做一次自动补时间戳。

```python
def sync_review_status(review: ManualReview) -> ManualReview:
    """把 pending 的裁决统一打上时间戳，方便审计。"""
    stamp = now_iso()
    for decision in review.decisions:
        if decision.verdict != "pending" and not decision.decided_at:
            decision.decided_at = stamp
            if not decision.reviewer:
                decision.reviewer = review.reviewer
    if review.overall != "pending" and not review.reviewed_at:
        review.reviewed_at = stamp
    return review
```

逐条拆开看：

1. **时间戳在循环外取**（`stamp = now_iso()`）。同一轮里所有补的时间戳完全一致——保证一次评审在时间线上是一个点，而不是散开的一段区间。
2. **只给非 `pending` 的裁决补**。`pending` 表示还没裁决，打时间戳没有意义。
3. **不覆盖已有值**（`not decision.decided_at`）。评审人自己填的时间（比如离线评审后补录）会被尊重。
4. **顺带补评审人**。decision 级别的 `reviewer` 为空时用 `review.reviewer` 兜底，所以模板里那三个 `""` 不需要手填。
5. **顶层同理**。`overall` 不是 `pending` 且 `reviewed_at` 为空时补上 `reviewed_at`。

`now_iso()` 来自 `util.py`，返回 UTC 的 ISO8601 字符串（以 `Z` 结尾，秒级精度）。

**效果**：§5.2 那份手填 JSON 里 `decided_at` 全是 `null`，跑完 `check --review` 后，报告里出现的是 `- 评审时间：2026-10-10T01:20:29Z`，对应的 `report.json` 里每条 decision 也都带上了同一个 `decided_at`。这就是审计记录的形态——**谁（reviewer）、在什么时候（decided_at）、对哪条问题（question_id）、做了什么裁决（verdict）、理由是什么（note）**，五个要素齐全。

两个容易忽略的点：`sync_review_status()` 是**原地修改**的，直接改 `review` 对象并返回同一引用，调用发生在 `apply_review()` 之前，所以 `manual_summary` 里存的 `review.to_dict()` 已是补好时间戳的版本；另外它**只在传了 `--review` 时**才被调用，不带 `--review` 时 `manual_summary["review"]` 是 `None`，报告直接走「未执行人工质检」分支。

## 7. 三条实操建议

**第一，`reject` 一定要配 `overall`。** 单条 `verdict=reject` 不会进 `unresolved`，所以既不会触发 `REVIEW` 也不会触发 `REJECT`，真正决定命运的是 `overall`：

| 你填的 | 你会得到的 |
| --- | --- |
| 某条 `reject` + `overall=approve` | `PASS`（若无硬性阻断）——**很可能不是你要的** |
| 某条 `reject` + `overall=reject` | `REJECT` ✅ |
| 某条 `reject` + `overall=pending` | `REVIEW`（报告显示「未执行人工质检」） |

**第二，`followup` 是「我需要更多信息」，不是「通过」。** 它和 `pending` 一样会进 `unresolved`，最终卡在 `REVIEW`。这是对的——表示「这条暂时没法下结论，需要补材料」。用它时请在 `note` 里写清**需要什么材料**，否则下一轮评审人还是不知道该做什么。

**第三，硬性阻断不能靠签字绕过。** 如果你拿到「人工状态：**人工通过但硬性阻断未豁免**」，说明自动侧有硬性检查项没达标（`ADM-01` / `ADM-02` / `MS-01` / `MS-03` 之一）。去报告「四、三级自动质检」总表里找「硬性阻断」列非 `—` 的行，再看该闸门明细里带 🔒 且判定为 ❌ 的检查项。**回到上游修数据**（换仓库、换里程碑、把快照钉到正确的 ref），而不是在评审文件里改字。

最后别搞混两套东西：**5 个固定问题**（H-01~H-05，来自 `MANUAL_QUESTIONS` 常量，在报告第五节，固定不变）和**复核队列**（来自 `build_review_queue()`，在报告第六节，每次跑都不同）。评审时建议**先看第六节**知道机器在纠结什么，**再逐条回答第五节**给出定性判断。

## 本章小结

- **为什么需要人工**：自动质检是纯函数，只能处理可结构化的事实。三类问题机器判不准——**法务判断**（许可证边界，`ADM-04` 拿到 1.0 也不等于授权清晰）、**领域判断**（任务隐含前提，`MS-03` 的字数只是代理指标）、**价值判断**（阈值边缘该不该放行）。
- **为什么单轮**：人工是最贵的一环。单轮同时控制成本和保证留痕——只做一次，但必须逐条给出裁决与理由，并自动打时间戳。
- **5 个固定问题**（H-01 ~ H-05）覆盖上述盲区，每条带 `why` 解释「为什么机器判不准」。其中 H-05（快照是否遗漏 submodule / LFS / 私有依赖）在自动侧**没有对应检查项**。
- **取值语义**：`decisions[].verdict` ∈ {`pending`, `accept`, `reject`, `followup`}；`overall` ∈ {`pending`, `approve`, `reject`, `rework`}。`unresolved()` 只把 `pending` / `followup` 算作未裁决，**单条 `reject` 不阻断，必须靠 `overall` 生效**。
- **复核队列三个触发条件**：硬性项得分 `< 1.0`（哪怕已通过）、普通项得分落在 `[0.4, 0.75)`、检查项未过 `pass_at`。硬性项即使通过也要人看，因为它是一票否决项，非满分通过是在试探边界。
- **合并规则**（`apply_review()`）四条主干：人工未提供 → 最多 `REVIEW`，不得放行；人工 `reject`/`rework` → 无条件 `REJECT`；`approve` 但有未裁决项 → 保持 `REVIEW`；`approve` 且全部裁决完毕 → 无硬性阻断时依自动分给 `PASS`/`REVIEW`（自动 `REJECT` 会被提升为 `REVIEW`），**有硬性阻断则仍为 `REJECT`**（实现里没有「显式豁免」的表达方式）。另有未知 `overall` 的 fail-safe 分支 → `REVIEW`。
- **完整闭环**：`init-review` 生成带 `_instructions` 和 `_question_bank` 的模板 → 评审人填 `verdict` / `note` / `overall` → `check --review` 重跑，`sync_review_status()` 自动补齐 `decided_at` / `reviewed_at` / `reviewer`，形成五要素齐全的审计记录。

下一章看这些结论如何被渲染成报告，以及怎么接进 CI——包括退出码约定和一份可直接用的 GitHub Actions workflow。
