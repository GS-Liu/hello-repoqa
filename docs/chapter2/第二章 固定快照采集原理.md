# 第二章 固定快照采集原理

> **本章导读**：本章讲清"固定快照"到底意味着什么、为什么必须钉在 commit sha 上、以及采集层如何做到**同一套质检规则同时支持在线 API 与离线 fixtures**。核心文件是 `ghsqa/collector.py` 与 `ghsqa/models.py`。

---

## 2.1 为什么必须"固定"

&emsp;&emsp;先看一个真实场景。

&emsp;&emsp;2026 年 3 月，你用 `main` 分支采集了某个仓库，生成了 12 个任务，报告显示"测试文件 34 个、Milestone 有 9 个任务"。三个月后有人质疑这批任务的质量，你重新跑一遍采集——**结果全变了**：

- 主分支往前跑了 200 多个 commit；
- 当时的 Milestone 已被关闭，issue 被重新归类；
- 目录结构重构过，文件数从 340 变成了 512。

&emsp;&emsp;你**无法还原当时的判断依据**。那份报告成了一张废纸。

&emsp;&emsp;问题的根源在于：**`main` 不是某个具体的东西，它是一个会移动的指针。**

### commit sha 才是不可变锚点

&emsp;&emsp;Git 的对象模型里，只有 commit sha 是内容寻址的——它由提交内容（tree、parent、author、message）哈希得到。**同样的 sha，永远是同一份代码。**

&emsp;&emsp;所以本项目的采集流程强制走这条链路：

```
分支名/标签  ──解析──▶  commit sha  ──采集──▶  快照
   (可变)                  (不可变)              (可复现)
```

&emsp;&emsp;对应到代码，`Snapshot.pinned_ref` 优先返回 `RepoFacts.commit_sha`：

```python
# models.py
@property
def pinned_ref(self) -> Optional[str]:
    if self.repo and self.repo.commit_sha:
        return self.repo.commit_sha
    return self.request.ref
```

&emsp;&emsp;注意这个属性的**优先级设计**：只有当快照里确实记录了 commit sha 时，才用它；否则退回用户传入的 ref。这保证了 `pinned_ref` 始终反映"这份快照实际钉在哪"。

### `ADM-03` 会为此扣分

&emsp;&emsp;质检环节专门有一项检查这个：

```python
def snapshot_pinned(snapshot: Snapshot) -> CheckOutcome:
    """固定快照的核心要求：必须钉在不可变的 commit sha 上。"""
    pinned = snapshot.pinned_ref
    if not pinned:
        return CheckOutcome.fail("快照未被钉住：既没有 commit sha 也没有 ref")
    looks_like_sha = len(pinned) == 40 and all(ch in "0123456789abcdef" for ch in pinned.lower())
    if not looks_like_sha:
        return CheckOutcome.partial(
            0.4, "快照仅钉住可变 ref（%s），建议解析为 commit sha 后再采集" % pinned,
            measured={"pinned_ref": pinned, "immutable": False},
        )
    return CheckOutcome.ok("快照已固定在 commit %s" % pinned[:12],
                           measured={"pinned_ref": pinned, "immutable": True})
```

&emsp;&emsp;这是一个**部分得分**的典型例子：只钉了分支名不会直接判死（得 0.4），但会明确标出"不可变"为 `False`，提醒你这里有问题。它的权重是 **1.5**——高于大多数检查项，因为可复现性是整个流程的基石。

## 2.2 事实层与规则层解耦

&emsp;&emsp;这是本项目最重要的架构决策。看一张对比图：

```
❌ 耦合的写法
  规则函数 ──直接调用──▶ GitHub API
  （规则里混着 HTTP 请求、分页处理、字段解析）

✅ 本项目的写法
  collector ──产出──▶ Snapshot（纯数据）
  rules     ──只读──▶ Snapshot
  （规则里没有任何网络代码）
```

&emsp;&emsp;在 `rules.py` 里，**每条规则都是纯函数**：

```python
Check(
    id="REPO-03", title="测试与回归护栏", gate="REPO",
    fn=test_coverage,          # 签名永远是 Snapshot -> CheckOutcome
    weight=1.5, ...
)
```

&emsp;&emsp;规则不认识 HTTP，不认识 JSON，只认识 `Snapshot`。这个约束带来了三个非常实际的好处：

| 好处 | 说明 |
| --- | --- |
| **CI 可回归** | 规则用 fixtures 跑，不受网络与 API 配额影响，秒级完成 |
| **可离线开发** | 调试规则时不需要反复请求 API |
| **易扩展数据源** | 接入 GitLab/Gitee 只需产出同样的 `Snapshot`，**规则层零改动** |

&emsp;&emsp;规则层的实现细节会在[第三章](../chapter3/第三章%20三级自动质检设计.md)展开。本章聚焦采集层如何产出这个 `Snapshot`。

## 2.3 两种数据源

&emsp;&emsp;采集层支持两种数据源，通过 `collect()` 统一分派：

```python
def collect(request: SnapshotRequest, source: str = "api", fixtures_dir: Optional[str] = None, ...) -> Snapshot:
    """统一入口：按 source 分派到 API 或 fixtures 采集。"""
    if source == "fixtures":
        if not fixtures_dir:
            raise CollectError("source=fixtures 时必须提供 fixtures_dir")
        return collect_from_fixtures(request, fixtures_dir)
    if source != "api":
        raise CollectError("未知数据源：%r（可选 api / fixtures）" % source)
    return collect_from_api(request, client=client, max_pages=max_pages, ...)
```

### 数据源一：`api` —— 在线采集

&emsp;&emsp;走 GitHub REST API v3。`GitHubClient` 是一个极简客户端，只实现采集所需的最小接口集：

```python
class GitHubClient:
    API = "https://api.github.com"

    def __init__(self, token: Optional[str] = None, timeout: int = 30) -> None:
        self.token = token or os.environ.get("GITHUB_TOKEN") or os.environ.get("GH_TOKEN")
        self.timeout = timeout
```

&emsp;&emsp;注意 token 的读取顺序：**显式传入 > `GITHUB_TOKEN` > `GH_TOKEN`**。Token 是可选的——匿名请求也能工作，只是配额低（每小时 60 次）。对于本项目这种单仓库少量请求的场景，匿名通常够用。

&emsp;&emsp;客户端还提供了分页支持，并用 `max_pages` 封顶：

```python
def get_paged(self, path: str, params=None, max_pages: int = 5, per_page: int = 100) -> List[Any]:
    collected: List[Any] = []
    for page in range(1, max_pages + 1):
        params["page"] = page
        chunk = self.get(path, params)
        if not chunk:
            break
        collected.extend(chunk)
        if len(chunk) < per_page:
            break
    return collected
```

&emsp;&emsp;`max_pages` 是一个**防御性设计**：像 `torvalds/linux` 这样的巨型仓库，贡献者列表可能有几千页。不封顶就会让一次采集跑上很久，甚至触发限流。默认 5 页（最多 500 条）对绝大多数仓库足够。

### 数据源二：`fixtures` —— 离线事实包

&emsp;&emsp;从本地 JSON 读取，**完全离线、可复现**。这是 CI 回归和本教程所有示例的基础。

&emsp;&emsp;fixtures 支持两种组织形式：

```
fixtures/
├── datawhalechina__hello-agents/     ← 目录形式（推荐，便于人工审阅）
│   ├── repo.json
│   └── milestones.json
└── acme__widget-toolkit.json         ← 单文件形式也支持
```

&emsp;&emsp;目录命名规则是 `owner__repo`（双下划线），由这一行决定：

```python
slug = request.repo.replace("/", "__")
```

## 2.4 API 采集的完整流程

&emsp;&emsp;`collect_from_api()` 的执行链路是固定的六步：

```
① /repos/{owner}/{repo}                    → 仓库元信息 + 默认分支
② /repos/{owner}/{repo}/commits/{ref}      → 解析为 commit sha
③ /repos/{owner}/{repo}/git/trees/{sha}?recursive=1  → 完整文件树
④ /repos/{owner}/{repo}/contributors       → 贡献者列表
   /repos/{owner}/{repo}/languages         → 语言构成
   /repos/{owner}/{repo}/commits           → 近期提交量
⑤ /repos/{owner}/{repo}/milestones         → 里程碑列表
⑥ /repos/{owner}/{repo}/issues?milestone=N → 任务明细
```

### 第②步：把 ref 解析成 sha

```python
default_branch = raw_repo.get("default_branch") or "main"
ref = request.ref or default_branch
commit = client.get("/repos/%s/%s/commits/%s" % (owner, name, ref))
commit_sha = (commit or {}).get("sha")
if not commit_sha:
    raise CollectError("无法把 ref %r 解析为 commit" % ref)
```

&emsp;&emsp;用户没指定 `--ref` 时，默认用仓库的 `default_branch`（而不是硬编码 `main`——有些仓库默认分支是 `master`、`develop` 甚至 `trunk`）。

### 第③步：一次性拉取完整文件树

&emsp;&emsp;这是整个采集里最关键的一次请求。用 `git/trees/{sha}?recursive=1` **递归拉取**，一次拿到所有文件路径：

```python
tree = client.get("/repos/%s/%s/git/trees/%s" % (owner, name, commit_sha), {"recursive": "1"})
files = [
    FileFacts(path=node.get("path", ""), size=node.get("size") or 0,
              sha=node.get("sha"), is_dir=node.get("type") == "tree")
    for node in (tree or {}).get("tree", [])
    if node.get("type") in ("blob", "tree")
]
```

&emsp;&emsp;**注意这里只保存路径、大小、sha 和类型，不保存任何文件内容。** 这是有意的：

- 质检需要的是**结构信号**（有哪些文件、分布在哪些目录），不是代码内容；
- 不拉取内容让采集保持轻量，几百个文件的仓库也能秒级完成；
- 避免把大量代码复制进快照带来存储与合规负担。

&emsp;&emsp;树里同时包含 `blob`（文件）和 `tree`（目录）两种节点，`is_dir` 字段把它们区分开。

### 第⑤⑥步：Milestone 与任务明细

&emsp;&emsp;里程碑用 `state=all` 拉取，并按截止时间排序：

```python
raw = client.get_paged("/repos/%s/%s/milestones" % (owner, name),
                       {"state": "all", "sort": "due_on", "direction": "asc"},
                       max_pages=max_pages)
```

&emsp;&emsp;这里有一个**性能优化**：只有当里程碑是用户指定的目标时，才去拉取它的 issue 明细：

```python
want = request.milestone
if want is None or str(ms.number) == str(want) or ms.title == want:
    ms.issues = _collect_issues(client, owner, name, ms.number, max_pages)
```

&emsp;&emsp;原因很实际：一个仓库可能有几十个里程碑，每个下面几十个 issue。全量拉取会产生大量请求。既然质检只需要评估目标里程碑，其余的拿聚合计数（`open_issues` / `closed_issues`）就够了。

&emsp;&emsp;匹配逻辑支持**编号或标题**两种方式，方便用户按习惯使用。

### Issue 采集保留了什么

```python
issues.append(IssueFacts(
    number=item.get("number", 0),
    title=item.get("title") or "",
    state=item.get("state") or "open",
    labels=[lab.get("name", "") for lab in (item.get("labels") or [])],
    assignees=[a.get("login", "") for a in (item.get("assignees") or [])],
    body_length=len(body),          # ← 只记长度，不存正文
    comments=item.get("comments") or 0,
    is_pull_request="pull_request" in item,
    ...
))
```

&emsp;&emsp;两个值得注意的设计：

1. **`body_length` 只记录长度，不保存正文。** 质检只需要判断"描述是否充分"（`MS-04` 用 120 字符作阈值），不需要正文内容。这既保护了隐私，也控制了快照体积。
2. **`is_pull_request` 标记。** GitHub 的 issues 接口**同时返回 issue 和 PR**，通过是否存在 `pull_request` 字段区分。不标记的话，PR 会被误算成任务，污染任务数统计。

## 2.5 结构信号推导：从文件清单到判断依据

&emsp;&emsp;拿到文件树之后，重头戏是 `derive_structure()`——它把一堆文件路径转换成质检真正需要用的**结构信号**。

```python
def derive_structure(repo: RepoFacts, files: Iterable[FileFacts]) -> RepoFacts:
    """根据文件清单填满 RepoFacts 上的结构类信号字段。"""
    file_list = [f for f in files if not f.is_dir]
    repo.files = file_list
    repo.file_count = len(file_list)
    ...
```

&emsp;&emsp;它会算出这些字段：

| 字段 | 含义 | 谁在用 |
| --- | --- | --- |
| `file_count` | 文件总数 | `ADM-07`、`REPO-07` |
| `code_file_count` | 代码文件数 | `REPO-03`、`REPO-07` |
| `test_file_count` | 测试文件数 | `REPO-03`、`MS-05` |
| `doc_file_count` | 文档文件数 | `REPO-01`、教程型识别 |
| `max_depth` | 目录最大深度 | `REPO-02`、`REPO-07` |
| `has_ci` | 是否配置 CI | `REPO-04`、`MS-05` |
| `has_manifest` | 是否有依赖/构建清单 | `REPO-04`、`REPO-05` |
| `has_tests_dir` | 是否有测试目录 | `REPO-03` |
| `has_readme` / `has_license_file` / `has_docker` / `has_gitignore` | 常见工程文件 | `REPO-01`、`ADM-04` |
| `top_level_entries` | 顶层条目列表 | `REPO-02` |

### 测试文件是怎么识别的

&emsp;&emsp;测试识别靠 `FileFacts.looks_like_test`：

```python
@property
def looks_like_test(self) -> bool:
    low = self.lower
    if "/test/" in low or "/tests/" in low or low.startswith("tests/") or low.startswith("test/"):
        return True
    if "__tests__" in low:
        return True
    name = low.rsplit("/", 1)[-1]
    return name.startswith("test_") or name.endswith("_test.py") or ".test." in name or ".spec." in name
```

&emsp;&emsp;它同时覆盖了三种主流约定：

- **目录约定**：`tests/`、`test/`、`__tests__/`（JS 生态）
- **Python 约定**：`test_*.py`（pytest）、`*_test.py`
- **JS/TS 约定**：`*.test.ts`、`*.spec.js`

&emsp;&emsp;注意 `lower` 属性先把路径统一成小写并用 `/` 分隔：

```python
@property
def lower(self) -> str:
    return self.path.lower().replace("\\", "/")
```

&emsp;&emsp;这个处理让规则在 Windows 和 Linux 上行为一致——否则 `src\Tests\Foo.cs` 在 Windows 上可能识别不到。

### 代码 vs 测试：`elif` 不能改成 `if`

&emsp;&emsp;看这段分类逻辑：

```python
for item in file_list:
    ...
    if item.looks_like_test:
        repo.test_file_count += 1
    elif item.ext in CODE_EXTENSIONS:
        repo.code_file_count += 1
    ...
```

&emsp;&emsp;这里用的是 **`elif` 而不是 `if`**，这一点很关键。

&emsp;&emsp;因为测试文件本身也是代码文件（`test_agent.py` 也是 `.py`）。如果用 `if`，它会**同时被计入 `test_file_count` 和 `code_file_count`**，导致：

- `test_ratio = test_file_count / code_file_count` 被系统性高估；
- `code_file_count` 虚高，影响 `REPO-07` 的规模判断。

&emsp;&emsp;用 `elif` 明确语义：**先把测试文件挑出来，剩下的才算业务代码**。这是一个很小但很典型的工程细节——分类体系必须互斥。

### CI 路径的识别

&emsp;&emsp;`CI_HINT_PATHS` 覆盖了主流 CI 系统的配置文件：

```python
CI_HINT_PATHS = (
    ".github/workflows/",       # GitHub Actions
    ".gitlab-ci.yml",           # GitLab CI
    ".travis.yml",              # Travis
    "azure-pipelines.yml",      # Azure Pipelines
    "Jenkinsfile",              # Jenkins
    ".circleci/config.yml",     # CircleCI
    "appveyor.yml",             # AppVeyor
    ".drone.yml",               # Drone
)
```

&emsp;&emsp;判定时同时用三种匹配方式，兼顾目录与文件：

```python
def _is_ci_path(low: str) -> bool:
    return any(low == hint or low.startswith(hint) or low.endswith(hint) for hint in CI_HINT_PATHS)
```

## 2.6 归档校验：字节级凭据

&emsp;&emsp;commit sha 保证了"采的是哪份代码"，但还差一层：**怎么证明我手上的文件确实等于那个 sha 的内容？**

&emsp;&emsp;`_attach_archive()` 解决这个问题——下载 tarball 并记录 SHA256：

```python
def _attach_archive(snapshot, client, owner, name, commit_sha, archive_dir) -> None:
    """下载 tarball 并记录 sha256，让"固定快照"具备可验证的字节级凭据。"""
    if not archive_dir:
        return
    os.makedirs(archive_dir, exist_ok=True)
    target = os.path.join(archive_dir, "%s-%s.tar.gz" % (name, commit_sha[:12]))
    url = "%s/repos/%s/%s/tarball/%s" % (client.API, owner, name, commit_sha)
    ...
    snapshot.archive_bytes = os.path.getsize(target)
    snapshot.archive_sha256 = sha256_file(target)
```

&emsp;&emsp;下载采用**分块流式**写入，避免大文件占满内存：

```python
with urllib.request.urlopen(request, timeout=client.timeout) as response:
    with open(target, "wb") as fh:
        while True:
            chunk = response.read(1 << 16)     # 64 KB
            if not chunk:
                break
            fh.write(chunk)
```

&emsp;&emsp;如果下载失败（网络问题、仓库过大），**不会中断整次采集**，而是降级为一条 warning：

```python
except (urllib.error.HTTPError, urllib.error.URLError) as exc:
    snapshot.warnings.append("归档下载失败，快照仍以 commit sha 固定：%s" % exc)
    return
```

&emsp;&emsp;这个降级策略体现了优先级判断：**commit sha 是必需的，tarball 是加分项**。没有 tarball，快照依然可以完整复现（重新按 sha 拉一次即可）；但如果因为下载失败整次采集作废，就本末倒置了。

&emsp;&emsp;如果不想下载归档（比如仓库有几个 GB），用 `--no-archive` 跳过。

## 本章小结

&emsp;&emsp;本章的核心要点：

1. **固定快照必须钉在 commit sha 上。** 分支名是会漂移的指针，只有内容寻址的 sha 才能保证可复现。`ADM-03` 会为此检查并扣分（权重 1.5）。

2. **事实层与规则层解耦是本项目的架构基石。** 采集器只产出 `Snapshot`，规则只读 `Snapshot`。这让同一套 21 条规则同时支持在线 API 与离线 fixtures，也让规则能在 CI 里稳定回归。

3. **API 采集链路固定六步**：解析 ref → 拉文件树 → 采集贡献者/语言/提交 → 拉里程碑 → 按需拉 issue 明细。其中**只对目标里程碑拉取明细**是关键的配额优化。

4. **只存结构信号，不存内容。** 文件只保留路径/大小/sha，issue 只记录 `body_length` 而非正文——既保护隐私，也让采集保持轻量。

5. **`derive_structure()` 里的两个细节**：测试文件识别覆盖 Python/JS/目录三种约定；代码与测试计数必须用 `elif` 互斥，否则 `test_ratio` 会被系统性高估。

6. **归档校验提供字节级凭据**，但它是加分项而非必需项——下载失败会降级为 warning，不会作废整次采集。
